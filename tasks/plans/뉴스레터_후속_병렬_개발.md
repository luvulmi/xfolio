# T04 이후 뉴스레터 병렬 개발 계획

- 작성: 2026-11-04 · 갱신: 2026-11-05, Asia/Seoul
- 상태: G0~G2 구현·격리 통합 완료. G3 정시·유료 요약/G4 운영/G5 오후 인수는 진행 전
- 출발점: 요청 당시 사용자 확인 기준 T01~T03 완료, **T04는 다른 세션에서 진행 중**이었다. 계획 작성 중 해당 세션이 WBS와 [T04 계획](아침_뉴스레터_편성과_검사.md)을 구현·격리 검증 완료로 갱신했다. 후속 착수는 G0에서 결과·공통 계약·기준 revision을 인수한 뒤 진행한다. 파일 존재만으로 인계를 대신하지 않는다.
- 범위: T05~T09의 병렬 착수 조건·담당 범위·통합 순서. 후속 사용자 요청으로 T04 결과·계약 인수와 T05/T06/T08의 독립 환경 병렬 착수까지 실행한다. 운영 개시는 G3/G4 인수로 판단한다.

## 목표와 진행 방식

**관리자 화면을 만드는 동안 자동 전송과 배포 준비를 함께 진행**한다. 공통 데이터 형식과 담당 파일을 먼저 정하고, 기능별 시험을 마친 결과를 순서대로 합친다. 병렬 개발의 목적은 앞 작업 전체가 끝날 때까지 기다리는 시간을 줄이는 것이다.

권장 동시 구현은 최대3개 세션이다. T04 진행 중에는 `T04 + T05 준비 + T08 준비`, T04 인계 후에는 `T05 + T06 + T08 준비`로 배치한다. 통합 담당은 이와 별개의 기능을 동시에 개발하기보다 공통 계약과 합치기·회귀 검증에 집중한다. 세션 이름은 역할 제안이며 실제 생성된 세션을 뜻하지 않는다.

작업별 기준 공수·목표 날짜는 WBS에서 관리한다. 이 문서는 그 작업을 **언제 시작할 수 있고, 무엇이 준비돼야 마칠 수 있는지**를 설명한다. 프로젝트 기획서는 사용자의 별도 수정 요청이 있을 때만 갱신한다.

T04에서 관측한 `newsletter.py`, `newsletter_store.py`, `db/newsletter.py`, `0005_morning_newsletter`를 인계 대상으로 삼는다. [편성/발송 검사 계약](../verification/integration/아침_뉴스레터_편성과_발송_검사.md)의 공개 입력/출력·저장 함수와 테스트 근거를 함께 받고, 그 시점의 revision을 기준으로 후속 작업을 시작한다.

특히 **관리자가 저장한 일시 중지 설정을 worker가 그대로 읽고, 전송 직전에 다시 확인**해야 한다. T05와 T06이 설정 테이블이나 기본값을 각각 만들지 않는다. T06 발송 결과의 쓰기와 T05 이력 화면의 읽기도 하나의 계약으로 맞춘다.

## 4. 파일과 DB 변경 담당

| 범위 | 기본 담당 | 병렬 작업 규칙 |
| --- | --- | --- |
| T04 `newsletter*.py`·`db/newsletter.py`·0005·관련 시험/계약 | 기존 T04 세션 | T04 인계 전 직접 수정 금지. 인계 후에도 변경 요청을 먼저 계약에 반영 |
| `frontend/`·`src/xfolio/api/`·관리자 시험·`contracts/openapi.json` | T05 | 인증/세션/CSRF를 유지하고 T06의 발송 상태 정의를 소비. OpenAPI는 API 소스에서 생성 |
| `src/xfolio/jobs/` 등 신규 worker·Telegram adapter·outbox·관련 시험 | T06 | 새 경로는 구현 시 확정. T04 편성/검사를 복제하지 않고 호출. 설정 쓰기는 T05 소유 |
| 새 Docker/Compose·비공개 접근/백업/운영 문서 | T08 | 기존 `deploy/cloud/` 시험 자산과 구분. 실행 명령 확정 전에는 연결부를 가정으로 명시 |
| `migrations/env.py`·revision 연결·공통 DB metadata | 통합 담당 | 각 작업이 필요한 DDL을 제안하되 번호·부모 revision·적용 순서는 통합 담당 한 명이 관리 |
| `pyproject.toml`·`uv.lock`·공통 CLI·루트 README·WBS·작업 목차·CI | 통합 담당 | 각 세션은 필요한 변경을 인계 목록에 제출하고, 통합 시 한 번씩 반영 |

**migration 순서:** T04의0005 최종 확인 → T05 설정 저장 등 필요한 변경 → T06 outbox 변경 → T09 추가 변경 순으로 단일 계보를 유지한다. 이미 T04에 포함된 테이블은 재사용하고 중복 생성하지 않는다. 다음 번호는 실제 인계 시 배정하며 병렬 세션이 같은 번호를 선점하지 않는다. 새 변경이 없다면 불필요한 migration을 만들지 않는다.

**작업 공간:** 후속 구현은 작업별 브랜치·독립 worktree를 권장한다. 새 worktree에는 현재 미커밋 T04/정책 변경이 자동으로 따라가지 않는다. 착수 시 공통 기준 revision과 최신 운영 정책을 명시하고, 필요한 변경을 승인된 커밋 또는 검토한 패치로 전달한 뒤 확인한다. 계획 작성만으로 커밋이나 worktree 생성이 실행된 것은 아니다.

**시험 DB:** 세션마다 별도 DB 또는 고유 schema·컨테이너/포트를 사용하고 자신의 시험 자원만 정리한다. 통합 migration 시험은 통합 담당의 별도 DB에서 수행한다. 운영 DB나 다른 세션의 schema를 초기화하지 않는다.

각 담당은 변경 범위·계약 변경·시험 결과·미확인 항목을 인계한다. Python 기능 변경은 관련 무통신 시험·Ruff·격리 DB 시험을 수행하고, 통합 버전에서 전체 `uv run pytest`를 실행한다. 프론트 변경은 `npm test`·`npm run build`와 관련 Playwright 흐름을 확인한다. 단독 시험 통과가 통합 시험을 대신하지 않는다. 변경 없는 전체 시험을 여러 세션에서 중복 실행하지 않는다.

실제 Telegram 송신·유료 API·AWS 자원 생성/배포·운영 migration은 해당 실행 범위가 허용된 뒤 진행한다. 이 계획은 운영 실행 승인이 아니며 매회 뉴스레터 사람 승인을 추가하는 정책도 아니다.

요청 당시 WBS의 **22h는 T04를 포함한 순차 작업 기준**이었다. 작성 중 다른 세션이 T04 완료를 반영해 현재 T05 이후 잔여 기준은**20.25h(A16+B4.25)**로 갱신했다. 이는 T04 기준1.75h를 완료 범위로 옮긴 결과이며 병렬화에 따른 절감이 아니다. 공통 계약/통합 추가 작업은 실행 시 확인하고, 이 수치를 병렬 실행의 새 실측/확정 견적으로 사용하지 않는다.

병렬 실행에서는 각 세션의 능동 시간을 합한 값과 전체 달력 경과시간을 따로 기록한다. 예를 들어 두 세션이 동시에1시간 작업하면 세션 시간 합계는2시간, 경과시간은1시간이다. 사용자 직접 작업과 정시/외부 대기도 별도로 기록한다. 공통 계약 조율·합치기·추가 회귀에 든 시간을 실제 발생 작업에 계상하고 중복 계산하지 않는다.22h를 세션 수로 나누거나 병렬화만으로 기준 공수를 할인하지 않는다.

WBS의 일별5h는 기존 A+B 합산 배정 상한이다. 병렬 작업에도 각 세션 시간 합계와 사용자 시간을 기준으로 확인한다. 동시 실행 세션별로5h씩 사용할 수 있다는 뜻이 아니다. 실행 인계 시 실제 담당·공수를 확인해 WBS 배치를 갱신하며, 이 계획은 그 일별 표를 별도의 확정 시간표로 복제하지 않는다.
