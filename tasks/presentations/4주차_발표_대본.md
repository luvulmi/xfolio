# 4주차 발표 대본 | 풀스택 2주 MVP

- 갱신: 2026-10-28, Asia/Seoul · 약 4~5분
- 화면 자료: [4주차 개발 계획](4주차_개발_계획.md). 기울임꼴은 발표 동작이다.

## ❶ 확정 기획과 기술 선택

*편성 표와 세로 구조도를 보여준다.*

이 프로젝트는 미국 시장 정보를 X에 올리는 기능에 더해, 4년차 풀스택 개발자로서 검토와 승인, 데이터 정합성, 장애 처리와 배포를 설명할 수 있는 포트폴리오를 만드는 것이 목표입니다.

아침에는 두 지수 종가와 등락률을 한 글로 묶고 중요 뉴스를 최대 두 글 더합니다. 추가 뉴스는 발견 즉시 올리는 방식에서 바꿨습니다. 낮 동안 매시간과 17시 30분에 감시한 후보를 모아, 18시에 새로운 중요 사건을 최대 두 건 발행합니다. 적격 뉴스가 없으면 채우지 않습니다. 마지막 수집과 근거는 17시 45분까지 동결하고, 저녁 신규 전송 마감은 MVP 설정으로 18시 10분을 둡니다.

관리자는 React와 TypeScript, 백엔드는 FastAPI, DB는 PostgreSQL로 정했습니다. 기존 Python의 지수·뉴스 수집과 Luna 분석 코드를 재사용합니다. 관리자는 후보 목록과 상세의 두 화면에서 근거와 검증 결과를 보고 정확한 버전을 승인하거나 보류합니다. 브라우저에서 직접 DB나 X를 호출하지 않습니다.

상세 기획에서는 아침과 저녁 각각 편성 전체를 일괄 승인하도록 정했습니다. 잘못된 초안은 보류한 뒤 CLI에서 기존 근거로 문안을 수정하거나 기사를 제외하고, 새 버전을 검증해 다시 승인합니다. 저녁 17시 45분 이후 새 기사나 근거는 추가하지 않고 정정·충돌이 발견되면 편성 전체를 보류합니다. 이 기준은 구현 전 계약입니다.

아침은 새 미국 거래일 종가가 있을 때만, 저녁은 KST 날짜가 미국 거래일인 날에 운영합니다. 따라서 휴장 없는 주간에는 월요일 아침을 건너뛰고 토요일 아침에 금요일 종가를 전달합니다.

배포는 Lightsail 한 대에 React 정적 화면, API, 별도 worker를 Docker Compose로 올리고 기존 Neon을 유지합니다. worker 한 프로세스가 Python 스케줄러를 실행하되 중복 발행은 DB의 고유 키와 상태 점유로도 막습니다. 중요한 자동 처리 오류나 요금 한도 부족, X 결과 불명은 Telegram으로 알립니다.

## ❷ 2주 개발 범위

*15시간씩 배정한 표를 짚는다.*

5주차와 6주차에 각각 15시간, 총 30시간을 배정합니다. 이를 위해 화면은 두 개, 업무 API는 여덟 개, worker와 AWS 서버는 하나로 제한했습니다.

5주차에는 React와 FastAPI의 골격, PostgreSQL migration과 인증을 만들고 목록·상세·버전 승인을 연결합니다. 기존 가상 뉴스 한 건 미리보기를 아침 뉴스가 없을 때와 한 건·두 건인 경우로 확장합니다. 주차 말 기준은 로그인한 React 화면에서 아침 후보를 검토하고 정확한 버전을 승인할 수 있는 것입니다.

6주차에는 낮 감시와 18시 편성, X 글별 결과와 비용 상태, Telegram 중요 알림을 연결합니다. Docker와 AWS 배포, CI 검사와 핵심 E2E도 이 주차에 묶었습니다. 전송 타임아웃과 구버전 승인, 중복 호출, 마감·한도 초과를 시연할 수 있게 시험합니다.

RDS나 ECS, Redis와 Celery, Terraform, 고급 차트와 완전 자동 배포는 이번 두 주에서 제외합니다. 정해진 날짜에 기능을 많이 보여주는 것보다 핵심 흐름과 실패 처리의 근거를 남기는 데 집중합니다.

## ❸ 현재 진행과 남은 조건

*기존 자산과 새 작업을 나란히 짚는다.*

두 지수의 실제 조회와 거래일·등락률 계산, 뉴스 개발 수집기와 근거 모델, SQLite 커서가 있습니다. Luna는 가상 여섯 건에서 기계 검사를 통과했습니다. Neon 가상 저장과 기존 Streamlit의 로그인도 확인했습니다.

이 결과가 새 React 관리자나 FastAPI, AWS와 Telegram 구현이 끝났다는 뜻은 아닙니다. 이 부분은 이번 계획의 새 작업입니다. 뉴스 검색에서 무관 기사와 거시 누락 위험이 있었기 때문에, 실기사의 권한과 근거를 확인하고 가상 입력과 실제 처리를 구분하겠습니다.

예산은 월 5만 원을 유지합니다. 1GB AWS VM과 이전 최대 게시량의 X·AI 가정만 더하면 약 4만 7천 원이지만, 도메인과 백업, 실제 메모리는 아직 확인 전입니다. 2GB가 필요하면 같은 계산만으로 약 5만 6천 원이어서 예산을 다시 판단해야 합니다.

두 주 완료 목표는 reviewed MVP입니다. 무인 auto 활성화는 최소 다섯 미국 거래일의 예약·검토와 장애 시험을 통과한 뒤 결정합니다. X 인증과 실제 게시 승인, Telegram bot/chat, AWS·도메인은 개발 전에 준비하겠습니다.

## 예상 질문과 답변

**Q. 왜 Streamlit에서 React와 FastAPI로 바꾸나요?**

A. 빠른 가상 화면 검증에서 풀스택 포트폴리오로 목적이 구체화됐기 때문입니다. API 계약·인증·화면 상태와 승인 충돌을 직접 구현하고, 기존 Python 수집/분석은 재사용합니다. Streamlit 시험 성과는 보존합니다.

**Q. FastAPI와 worker를 왜 분리하나요?**

A. API 요청과 긴 수집·AI·게시의 실행 수명을 나누기 위해서입니다. API는 승인 상태만 저장하고 worker가 예약 시각·현재 버전·한도와 기한을 검사합니다. API 프로세스를 여러 개 띄울 때 스케줄러까지 중복 실행되는 구조를 피하고 DB 점유로도 방어합니다.

**Q. 18시에 정확히 두 건을 올리나요?**

A. 최대 두 건입니다. 적격 사건이 없으면 생략합니다. 낮에는 후보를 수집하고 17시 45분까지 완전 수집 결과와 근거를 동결해 18시 발행을 목표로 합니다. 18시 10분 이후 신규 전송은 차단합니다. 정각 실행 보장은 실제 시험으로 확인해야 합니다.

**Q. 자동 승인 오류는 무엇을 뜻하나요?**

A. LLM이 게시를 허락하는 기능이 아닙니다. Python의 자동 검증/발행 준비 gate가 예외를 내거나 검증 실패·구버전을 발행하려 하는 상태를 말합니다. 먼저 보류하거나 auto를 중단하고 Telegram으로 알립니다. 일반적인 승인 409 하나마다 푸시하지는 않습니다.

**Q. Telegram에서도 승인하거나 재게시할 수 있나요?**

A. MVP는 발신 전용입니다. 오류 코드와 작업 ID, 중단 상태, 관리자 링크만 보내고 조치는 인증된 관리자나 CLI에서 합니다. 같은 장애 알림을 억제하고 429/전송 실패도 저장합니다. VM 전체가 꺼지면 자체 봇도 동작하지 않으며 외부 생존 감시는 후속입니다.

**Q. 2주에 모두 가능한가요?**

A. 기존 수집·AI·가상 저장을 재사용하고 2화면·8API·단일 서버로 제한한 30시간 계획입니다. 새 공급자 확장이나 고급 화면은 넣지 않습니다. 계정·권한·허용 입력이 준비돼야 하며, 조건이 없으면 모의 검증과 실제 완료를 구분합니다. 첫 주에 아침 승인까지 연결되지 않으면 범위와 시간을 다시 배분합니다.

**Q. AWS DB도 RDS를 쓰지 않는 이유는요?**

A. PostgreSQL과 AWS를 모두 사용하는 목표는 유지하면서, 이미 확인한 Neon을 재사용해 배포할 자원과 비용을 줄였습니다. RDS·ECS를 썼다는 사실보다 트랜잭션·버전 승인·재시작 복구와 실제 측정으로 선택을 설명하려 합니다.

**Q. 무인 자동 게시도 두 주 안에 끝나나요?**

A. 자동 검증 gate와 실패 시험은 구현하지만 기본은 dry_run→reviewed입니다. auto 운영 활성화는 5거래일과 장애 시험 뒤입니다. 실제 X 게시와 Telegram 시험 발송은 사용자의 명시적 승인 범위에서 수행합니다.

**Q. 가장 보여주고 싶은 기술 사례는 무엇인가요?**

A. 오래된 버전 승인 시 409로 차단하는 사례, X 응답이 불명확할 때 중복 전송을 막는 사례, 한도 부족 시 유료 요청을 멈추고 알리는 사례입니다. 화면 시연·상태 이력·통합 테스트로 근거를 보여주겠습니다.
