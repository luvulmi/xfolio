## 승인 대상과 상태

운영자가 검토하는 후보는 기사 한 건이 아니라 **해당 날짜·계정·AM 또는 PM의 전체 편성 버전**이다. 아침은 지수 1글과 뉴스 0~2글, 저녁은 뉴스 1~2개의 독립 글이다. 저녁 적격 뉴스 0건이면 발행할 초안을 만들지 않고 편성 결과를 `no_content`로 요약한다. `no_content`는 실행 요약의 정상 결과이며 게시 job의 성공 상태를 대신하지 않는다.

승인은 문안·순서·근거·지수·계정·날짜가 고정된 버전 전체에 한 번 적용한다. 글별 체크박스·부분 승인은 없다. 기사 하나를 제외하거나 문안을 고치면 새 버전 전체를 검증·승인한다. 예시 JSON의 ID·시각·내용은 계약 설명용 가상 값이며 외부 전송 입력으로 사용하지 않는다.

| 현재 상태 | 상세 화면의 동작 | 서버 결과 |
| --- | --- | --- |
| `prepared` | 근거/검증 진행 중, 승인 비활성 | 검증 완료 전 승인 차단 |
| `validated` | `편성 전체 승인`, `보류` | reviewed·현재 버전·기한·예산·한도 검사 후 예약 또는 보류 |
| `approved` / `scheduled` | 승인자·시각 표시, `승인 철회·보류` | 첫 전송 전 보류 시 안전한 미전송 예약 해제 |
| `held` | 사유 표시, `CLI 수정 절차` 안내 | 같은 버전의 재승인 차단. 새 버전 검증 뒤 재승인 |
| `sending` | `남은 글 중단` | hold는 이후 전송을 중단. 이미 전송한 요청의 취소·삭제는 아님 |
| `published` | 글별 X ID·결과 읽기 | 승인·보류 변경 불가 |
| `partial` / `unknown` | 대조 필요·수동 복구 안내 | 자동 재전송·새 버전 교체 금지 |
| `failed` / `expired` | 사유·시도 기록 읽기 | 승인으로 실패/마감 우회 불가. 복구는 기존 CLI 정책 적용 |

`approved`는 감사상의 승인 사실이고 발행 대기는 `scheduled`다. 한 승인 트랜잭션에서 예약까지 완료한 응답은 `scheduled`를 반환한다. auto에서는 화면 승인 버튼을 숨기고 검증/예약 상태를 표시한다. 서버도 reviewed가 아닌 승인 요청을 거부한다. dry_run·synthetic 자료에는 X 발행 예약 승인을 부여하지 않는다.

## 화면 1 · 대시보드

- 첫 진입은 KST 오늘 날짜, AM/PM 전체, 상태 전체다. 날짜는 KST 편성 대상일이고 미국 거래일은 별도 열에 표시한다.
- 상단: 모드·현재 KST, 마지막 정상 수집/실패·미완료 구간, 최근 발행, 월 예상/예약/확정 사용액, 미해결 장애·알림 실패 수를 표시한다. 비용은 앱 원장이며 계정 전체 청구액이라고 쓰지 않는다.
- 목록: 날짜·편성·미국 거래일·현재 버전·뉴스 수·상태·보류 원인·발행 목표/마감·마지막 갱신. 행 선택으로 상세로 이동한다.
- 필터: 날짜·AM/PM·상태. 기본 20개·최대 50개, `target_date DESC, edition ASC, id ASC`의 안정 정렬과 불투명 cursor를 사용한다. cursor는 필터와 묶어 검증하며 변조/다른 필터 재사용은 422다. 필터 변경 시 cursor를 초기화한다.
- 수집 정상 0건, 운영일 아님, 수집 실패, 조건 불충족은 서로 다른 안내 문구다. 행이 없다는 사실만으로 수집 성공이나 정상 0건을 추정하지 않는다.
- 목록·summary는 첫 진입·수동 새로고침·변경 성공 때 조회한다. 실시간 스트리밍과 상시 polling을 추가하지 않는다. 마지막 조회 시각과 새로고침 버튼을 둔다.

## 화면 2 · 편성 상세

위에서 아래로 편성/계정/모드·상태 → 목표/마감/동결 시각 → 순서대로 완성된 글 → 글별 근거와 검증 → 승인/보류 → 전송 결과/이력 순으로 배치한다. AM은 지수부터 이어지는 스레드, PM은 독립 글이라고 표시한다.

각 글에는 원문 URL·출처명·발행/수집 시각·사건/사실 버전, 사용이 허용된 근거 위치, 주장과 숫자·단위·기간의 대응, 가중 길이 결과를 보여 준다. 기사 전문·비밀 토큰·민감한 HTTP 응답은 표시하지 않는다. `편성 전체 승인` 옆에 “이 버전의 모든 글을 예약합니다”를 표시하고 `보류`에는 짧은 사유 입력을 요구한다. 사유는 1~300자이며 키·원문 붙여넣기를 안내로 방지하고 서버에서도 로그용 민감 값 제거를 적용한다.

요청 중 버튼을 비활성화하되 서버의 원자적 검사로 경쟁을 막는다. 성공 뒤 상세와 목록/summary를 다시 조회한다. 요청 timeout이면 결과를 추정하지 않고 먼저 상세를 조회한다. 같은 결정의 재시도는 동일한 멱등 키와 본문을 사용한다. 사용자가 내용을 바꾸거나 다시 결정할 때 새 키를 만든다.

## 인증과 기존 8개 API

| endpoint | 상세 계약 |
| --- | --- |
| `GET /api/auth/login` | Google OIDC로 리다이렉트. 서버가 state/nonce를 검증할 임시 상태를 만든다. 복귀 주소는 같은 origin의 허용 경로만 사용 |
| `GET /api/auth/callback` | issuer·audience·만료·state/nonce·검증된 운영자 허용 목록을 확인하고 서버 세션 생성 후 목록으로 복귀 |
| `GET /api/auth/me` | 운영자 표시명·모드·허용 동작·CSRF 토큰 반환. 토큰은 메모리에만 보관하고 세션 교체 시 갱신 |
| `POST /api/auth/logout` | `X-CSRF-Token`과 same-origin 검사 뒤 세션 무효화. 204 반환 |
| `GET /api/drafts` | `date=2026-10-28&edition=PM&status=validated&limit=20` 및 cursor 조회. 필터 누락은 전체 |
| `GET /api/drafts/{id}` | 편성 ID에 대한 현재 버전·글·근거·검증·현재 결정 revision·이력/결과 반환 |
| `POST /api/drafts/{id}/decision` | `approve/hold`만 허용. `expected_version`, `expected_decision_revision`, `Idempotency-Key`, CSRF 검사 |
| `GET /api/operations/summary` | 수집 complete/partial/failed·운영일/정상 0건·비용·발행·장애/알림 요약. 기사별 상세는 상세 API로 조회 |

API와 React는 같은 HTTPS origin을 사용한다. 쿠키는 Secure·HttpOnly·SameSite=Lax로 설정하고, 세션 유휴 30분·절대 12시간을 초기 구현값으로 둔다. Google 토큰은 브라우저 저장소로 전달하지 않는다. 변경 요청은 쿠키만으로 허용하지 않고 CSRF 토큰과 Origin을 검사한다. 인증 응답과 근거가 포함된 응답에 `Cache-Control: no-store`를 적용한다.

미인증/만료 401은 로그인으로 안내한다. 비허용 운영자·CSRF 실패 403은 조치를 막고 이유를 표시한다. 409는 최신 상세를 조회해 변경된 버전/상태를 보여 주며 자동 재승인하지 않는다. 조회 5xx는 기존 자료에 “최신 확인 실패”를 표시하고 승인 버튼을 막는다.

## JSON 계약 예시

`GET /api/drafts`는 목록에 필요한 요약만 반환한다. `edition`은 AM/PM, 시간은 UTC ISO 8601이다. UI에서 KST로 변환한다. `id`는 편성의 안정 식별자, `version`은 변경 불가 콘텐츠 버전, `decision_revision`은 콘텐츠를 바꾸지 않는 승인/보류 상태 변경의 단조 증가값이다. DB의 구체적 키 형식은 migration에서 결정하되 이 세 의미를 합치지 않는다.

```json
{
  "items": [{
    "id": "edition_demo_pm",
    "target_date": "2026-10-28",
    "edition": "PM",
    "market_trade_date": "2026-10-28",
    "version": 3,
    "decision_revision": 4,
    "status": "validated",
    "news_count": 2,
    "scheduled_at": "2026-10-28T09:00:00Z",
    "expires_at": "2026-10-28T09:10:00Z"
  }],
  "next_cursor": null
}
```

상세 응답의 전체 필드는 구현 시 OpenAPI로 정의한다. 아래는 승인에 필요한 부분이다.

```json
{
  "id": "edition_demo_pm",
  "version": 3,
  "decision_revision": 4,
  "status": "validated",
  "mode": "reviewed",
  "synthetic": false,
  "validation": {"status": "passed", "blocking_reasons": []},
  "frozen_at": "2026-10-28T08:45:00Z",
  "posts": [
    {"position": 1, "kind": "news", "text": "가상 계약의 첫 글", "evidence_ids": ["e_demo_1"]},
    {"position": 2, "kind": "news", "text": "가상 계약의 둘째 글", "evidence_ids": ["e_demo_2"]}
  ],
  "allowed_actions": ["approve", "hold"],
  "publication": {"job_id": null, "posts": []}
}
```

위 `synthetic:false`는 실자료 편성의 스키마 예시다. 이 문서의 가상 문구·ID를 실자료로 표시하거나 실제 예약하는 fixture를 만들지 않는다. 위 합성 예시 데이터는 반드시 `synthetic:true`와 발행 불가로 저장하고 제품 경로에서는 dry_run 미리보기·승인 차단 시험에만 사용한다.

reviewed 정상 승인·경쟁·예약의 상태/저장 계층 시험은 별도 격리 DB와 강제 모의 전송 adapter에서 수행한다. 해당 계층의 합격 전제는 테스트 더블로 주입하며 제품의 synthetic 차단을 끄는 설정이나 우회 CLI는 만들지 않는다. 이 결과는 상태 전이·트랜잭션의 시험 근거이며 전체 제품 경로 합격과 다르다. 제품 검증을 포함하는 reviewed 정상 E2E에는 수집·보관·AI·요약 사용이 확인된 실자료 fixture가 필요하며, 확보 전이면 그 시험은 대기로 남긴다. 이때도 외부 송신은 강제 모의하고 실제 공급자/게시 DB·키·adapter에 연결하지 않는다. U12는 제품 경로에서 별도로 검증한다.

승인 요청은 `X-CSRF-Token`과 `Idempotency-Key: decision-demo-001` 헤더를 사용한다.

```json
{"action":"approve","expected_version":3,"expected_decision_revision":4}
```

성공 200은 “예약됨”을 뜻하며 “X 게시 완료”를 뜻하지 않는다.

```json
{
  "decision_id": "decision_demo_001",
  "applied": true,
  "replayed": false,
  "version": 3,
  "decision_revision": 5,
  "status": "scheduled"
}
```

보류는 새 멱등 키와 최신 revision으로 요청한다.

```json
{"action":"hold","expected_version":3,"expected_decision_revision":5,"reason":"둘째 글의 조건 표현 수정 필요"}
```

409 응답 예시는 다음과 같다. `current_version`과 revision은 인증된 운영자에게만 반환한다.

```json
{
  "error": {
    "code": "DECISION_CONFLICT",
    "message": "상태가 변경되었습니다. 최신 편성을 확인하세요.",
    "current_version": 3,
    "current_decision_revision": 6
  }
}
```

409 원인 코드는 `VERSION_CONFLICT`, `DECISION_CONFLICT`, `DEADLINE_PASSED`, `VALIDATION_BLOCKED`, `MODE_BLOCKED`, `QUOTA_BLOCKED`, `BUDGET_BLOCKED`, `TRANSMISSION_STARTED`, `IDEMPOTENCY_CONFLICT`로 구분한다. 필드/enum/사유 길이 오류는 422, 존재하지 않는 편성은 404다. 알 수 없는 서버 오류는 원문 없이 request ID를 반환한다.

## 멱등성·승인 경쟁·철회

1. 인증·CSRF를 먼저 확인한다. 멱등 키의 범위는 운영자 + 편성 ID + 결정 endpoint이며, 정규화한 요청 본문 hash와 원결정 결과를 기존 `operations_events` 감사 기록에 저장한다. 범위/키 유일 제약을 둔다. 별도 아홉 번째 저장 단위를 추가하지 않는다.
2. 같은 키·같은 본문 재전송이면 원결정 식별자를 반환하고 **현재 상태를 다시 변경하지 않는다**. 응답에는 `replayed:true`와 원결정 결과 및 현재 버전/revision/상태를 구분해서 반환한다. 같은 키·다른 본문은 409다.
3. 새 키이면 편성의 현재 버전·decision revision·상태를 잠금/compare-and-set으로 확인하고 예산·뉴스 한도 예약·결정 기록을 같은 트랜잭션에 반영한다. 구버전이나 오래된 revision이면 409다. PM 2글 편성에 한도가 1개만 남았으면 전체 승인 409로 처리하며 일부만 승인/예약하지 않는다. 잠금 순서는 API/worker가 일관되게 구현하고 실제 PostgreSQL 경쟁 시험으로 확인한다.
4. `approve(k1) → hold(k2) → approve(k1) 재전송`은 이전 승인 응답의 재전달일 뿐이며 현재 `held`를 유지한다. `approve(k3)`로 과거 revision을 전송해도 409다. 보류 뒤에는 새 콘텐츠 버전을 검증해야 한다.
5. `hold`와 worker의 첫 전송 점유가 경쟁하면 원자적 순서로 판단한다. 전송 전 hold가 이기면 새 전송 0건이다. 전송 점유가 먼저면 이미 시작한 요청은 대조/결과 기록하고 이후 글을 중단한다. hold 성공을 이미 시작된 요청 취소 성공으로 표시하지 않는다.

결정 변경 감사는 운영 기간 동안 보존한다. 과거 키를 삭제해 재전송이 새 승인으로 바뀌지 않게 한다. 영속 기록 실패는 결정 성공으로 응답하지 않으며 발행을 차단한다.

## 보류 뒤 수정과 동결

운영자 CLI는 보류된 편성의 현재 버전과 동결된 허용 근거를 읽고 문안 수정·기사 제외만으로 새 버전을 생성한다. 기존 버전은 보존하고 편성 ID 아래 새 버전 번호를 부여한다. 편성 job은 하나를 유지하고 첫 전송 전의 현재 draft 버전 참조만 원자적으로 교체한다. 이전 승인 철회·확실한 미전송 예약 해제·새 버전 저장/참조 교체를 함께 반영하고 감사 이력은 보존한다. 새 버전은 예약 없이 검증하며 재승인 시 전체 글 수의 한도를 다시 확보한다. 근거에 없는 수치·인과·해석을 입력하면 동일 검증에서 차단한다. CLI 명령 이름·파일 옵션은 구현 시 README에 정한다.

PM은 17:45 이후 신규 기사·새 사실·새 근거를 넣지 않는다. 게시 직전 재조회는 기존 사실을 무효화하는 정정·충돌 탐지에만 사용하며, 충돌이면 편성을 보류하고 해당 회차의 문안 수정이나 해당 기사 제외로 우회 재개하지 않는다. 충돌 없는 동일 근거에 대한 문구 수정/기사 제외는 첫 전송 전·마감 전 새 버전 검증·재승인으로만 가능하다. 아침 지수 수정치 처리는 R08의 별도 근거·시각 기록 규칙을 따른다.

최초 X 전송이 시작된 편성은 버전 교체를 금지한다. 일부 성공·unknown은 원 버전·글별 결과를 보존해 복구한다. 마감이 지났거나 수정 시간이 부족하면 해당 편성은 생략하며 다음 회차에 사실·중복·근거·승인을 새로 판단한다. CLI를 통한 새 버전 생성은 직접 게시 권한이 아니다.
