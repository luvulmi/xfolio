# Telegram 메시지 가독성 개선

- 수행일: 2026-11-06, Asia/Seoul
- 상태: 완료 — 구현·무통신/격리 DB 검증·실제 메시지/소스 전송의 API 수락 확인
- 관련: [T04 계획](../plans/아침_뉴스레터_편성과_검사.md#116-telegram-표시-형식-개선) · [09시 실제 수신](2026-11-06_09시_뉴스레터_재시험.md)

사용자는 09시 실제 수신본을 기획서의 Telegram 예시처럼 간결하게 바꾸고 변경본과 API 연결 소스를 받도록 요청했다. 가격/뉴스 재조회와 AI 재요약 없이 09시 DB 원본을 재사용했다. 원래 실제 발송 본문과 수락 이력은 변경하지 않았다. 기획서는 참조만 했다.

## 변경

- [표시 코드](../../src/xfolio/newsletter/presentation.py)를 분리하고 실제 [편성](../../src/xfolio/newsletter/edition.py)에서 호출한다. 날짜/요일/시각, 거래일, ETF 한 줄 가격/등락률, 일반 뉴스와 공식 AI 요약, 공통 출처/조회시각/뉴스 기준 순서다.
- 제목·구역은 굵게 표시하고 원문 URL은 `원문 보기` 링크로 표시한다. 일반 뉴스 원제와 중요도 선정 순서·링크는 유지한다. 가격 실패·분할/정정 등락률 보류·분배락·뉴스 장애·24시간 이전 보완 안내도 유지한다. 세부 가격 근거는 기존 DB 스냅샷에 남는다.
- [Telegram 연결](../../src/xfolio/jobs/telegram.py)은 `sendMessage`에 plain text와 native `entities`를 전달한다. HTML/Markdown 구문을 해석하지 않으며 링크 미리보기를 끈다. 한글·이모지의 UTF-16 위치를 검사하고 [outbox](../../src/xfolio/jobs/outbox.py)의 조각마다 서식 위치를 재계산한다.
- `MorningEdition.entities`의 기본값은 빈 튜플이다. 이전 payload의 hash를 먼저 검증하고 이전 본문·hash를 유지해 읽는다. 편성 유일 키, 송신 점유/시도/중복/불명 처리 규칙은 유지한다.
- 사용자 요청 소스 첨부에 `sendDocument`를 사용했다. `.env`가 아닌 실제 `telegram.py`만 첨부했으며 로컬 비밀 값이 파일 안에 없는지 전송 전에 검사했다.

## 실제 전송

같은 11/6 09시 편성의 ETF 3종목·뉴스 3건을 읽기 전용으로 조회했다. 본문은 598 UTF-16 단위, 원문 링크는 3개다. `형식 확인 · 11.06 09:00 수신 자료 재사용`을 표시해 시점을 알렸다. 기존 outbox 재발송 대신 이번 요청의 별도 확인본으로 전송했으며 배타 생성한 시도 파일로 중복 실행을 차단했다.

| 항목 | 결과 |
| --- | --- |
| 변경 메시지 | 09:27:18 KST `confirmed`, 동일 본인 private chat·유효 message_id 확인 |
| `telegram.py` 첨부 | 09:27:19 KST `confirmed`, 동일 본인 private chat·유효 message_id 확인 |
| 원래 09시 편성/발송 이력 | 전후 비교에서 동일 |
| 추가 가격/뉴스 수집·AI 호출 | 모두 0회 |
| 새 형식의 단말 표시 | 사용자 확인 전. API 수락만 확인 |

비밀·chat ID·message_id는 이 문서에 기록하지 않는다. 개별 시도·수락 근거는 Git 제외 `.cache/local_runtime/2026-11-06_format_{message,source}.{attempt,receipt}.json`에 보관한다. 임시 미리보기 본문은 실제 전송 확인 후 삭제한다.

## 검증

- 외부 API 없는 단위 시험 82건 통과. plain text 기본 동작, UTF-16 링크/굵게·조각 경계·잘못된 entity 차단·소스 첨부·수락 확인·편성/시간/휴장 정책을 확인했다.
- 격리 PostgreSQL `55438`만 허용한 관련 회귀 205건 중 204건 통과 뒤, 종목 코드 대신 이름을 표시하는 요구에 맞춰 기존 10종목 시험 1건을 갱신·재실행해 통과했다. 최종 표시 코드의 단위 82건도 재통과했다. 실제 사용자 DB는 시험 fixture로 사용하지 않았다.
- 최초 회귀에서는 무통신 검사기가 Windows asyncio 내부 socketpair까지 차단했다. 이벤트루프 내부 연결만 허용하도록 검사기를 고쳐 외부 API 차단을 유지했다. 이전 payload 시험은 불변 편성을 갱신하지 않고 이전 형식을 INSERT해 검증하도록 고쳤다.
- Ruff 정적 검사·format 421파일 통과. 변경 Markdown 상대 링크·UTF-8/BOM·diff 공백 검사 통과. 기획서와 OpenAPI 계약 변경 없음.
- 검증용 DB는 시작 전 종료 상태였으며 검증 후 다시 종료했다. 실제 로컬 관리자/DB는 유지했다.

## 남은 확인

휴대폰에서 제목 강조·기사 간격·`원문 보기` 동작을 확인한다. 확인 후 이 변경과 앞선 준비 오류 수정·09시 시험을 목적별로 검토해 커밋할 수 있다. 이번에는 커밋하지 않았다.

## 후속 · 뉴스 제목 한국어 번역

11/6 사용자는 다음 08시 발송에도 새 형식을 사용하는지 확인하고 뉴스 제목을 한국어로 번역한 뒤 영어 원제를 괄호에 표시하도록 요청했다. 새로 편성되는 08시 본문은 공통 renderer를 사용한다. 현재 Windows 예약은 11/6 하루 시험용이므로 다음 거래일의 반복 예약 완료를 뜻하지 않는다.

- [제목 번역](../../src/xfolio/ai/title_translation.py): 최종 선정 최대 3건의 제목만 `gpt-6-luna`로 1회 묶음 번역한다. 본문·매체·링크·공식 사실 원문을 제목 번역 API에 전송하지 않는다. [OpenAI Docs 구조화 출력](https://developers.openai.com/api/docs/guides/structured-outputs)을 확인해 Pydantic schema·`store=False`·도구 없음·자동 재시도 없음·20초 timeout을 적용했다.
- 한국어 제목 → 다음 줄 `(영어 원제)` → 매체/발행시각/원문 링크 순서다. 공식 발표의 한국어 AI 요약은 유지한다. 원제·기사 버전·중요도·중복 키와 수집 item payload는 바꾸지 않고 번역만 편성 payload에 최대90일 보관한다.
- 출처 ID/버전/원제와 순서·수치/퍼센트 표기를 대조하고 한국어·단일 행·URL 미포함을 검사한다. 의미·고유명사 번역 품질은 이 형식 검사만으로 보증하지 않는다. 번역 실패/예산 초과 시 `제목 번역 확인 불가`와 괄호 안 원제를 표시하고 편성을 partial로 남긴다. 정상 가격·기존 공식 요약·뉴스 전송은 유지한다.
- 동일 월 비용 잠금과 `news_title_translation` 용도 예약·사용량 정산을 사용한다. 0건에는 AI 호출이 없으며 같은 준비를 재실행해도 재번역하지 않는다. 마감 이후 유료 호출을 시작하지 않는다.
- 단위 91건, 격리 PostgreSQL 회귀 66건 통과. 제목 번역·출처/수치 불일치·예산 초과·불명 결과·원제 보존·비용1회·저장/재조회·08시 기본 형식·10종목/송신 통합을 확인했다. 마지막 경계 변경 후 관련 단위 재검증도 통과했다. 시험 DB는 종료했다.

실자료 3건 검증은 첫 시도에서 기존 `prices_valid_until=11/6 09:00 KST` 만료로 API 호출 전에 차단됐다. [공식 가격](https://developers.openai.com/api/docs/pricing)을 다시 확인했고 Standard 입력/출력은 100만 토큰당 USD0.10/0.50이었다. 기존 보수적 550/1100원 추정 단가를 유지하고 이번 진단 메모리 설정에만 10분 유효기간을 부여했다. 기존 로컬 단가 기한은 바꾸지 않았다.

이후 **실제 번역 요청 1회는 `TITLE_TRANSLATION_RESULT_UNKNOWN`**으로 끝나 실제 한국어 출력/청구 사용량을 확인하지 못했다. 불명 결과를 성공으로 표시하거나 자동 재시도하지 않았고 비용 원장에 **9.9000원 상한 예약**을 유지했다. 실제 청구가 9.9000원이라는 뜻은 아니다. 추가 진단은 외부 API 없이 원장의 상태/고정 오류 코드만 조회했다. 이후 발생 원인을 구분할 수 있도록 timeout/연결/HTTP 거절/인증/유량/응답 schema의 고정 오류 코드를 보강했다. 키·원제·외부 응답 원문을 실패 로그에 넣지 않는다.

Telegram 재전송·새 수집·기존 편성 덮어쓰기·기획서 수정·커밋은 하지 않았다. 다음 작업은 실제 번역 응답 문제 진단/품질 확인, 유효 단가 설정과 다음 거래일 08시 반복 운영 인수다.

이후 사용자가 최종본 재전송과 기획서 예산 추가를 명시 요청했다. 월명 번역의 숫자 검사 오류를 수정해 실자료3건 번역을 확인했고10:06:43 KST에 한국어/영어 병기 확인본1건의 API 수락을 확인했다. 앞선 불명/실패 예약은 보존한다. 기획서6번 예산만 추가했으며 [최종 전송·예산 기록](2026-11-06_최종_확인본과_운영_예산.md)을 따른다.
