## 확인한 현재 상태

- 기존 문서에는 운영자 1명·X 계정 1개, AM/PM 편성, 편성 전체 버전 승인, 2화면·8API, React/FastAPI/PostgreSQL·단일 worker·AWS 목표가 기록되어 있다. 다만 사용자는 이번 논의에서 관리자 2화면은 확정 제약이 아닌 예시이며 확장 가능하다고 정정했다. 최신 사용자 설명을 우선하고 화면 수를 고정하지 않는다. API 개수도 화면 재설계의 근거 없는 상한으로 사용하지 않는다.
- 시간·한도·중복·재시도·수동 복구 원칙·보존 정책은 운영 정책에 있다. 전부 새로운 기획 질문으로 되돌리지 않는다.
- API·저장 모델·화면 상세가 [MVP 계약](../verification/integration/2주_MVP_구현_계약.md)과 [관리자 계약](../verification/admin/관리자_화면과_승인_API.md)에 분산되어 있다. 제품 명세와 시험 근거를 구분할 필요가 있다.
- 발표 자료의 구현 전 설명만으로 현재 상태를 판단하지 않는다. 기술 구성과 [10/29 구현 기록](../logs/2026-10-29_실자료_검사와_관리자_승인_연결.md)에 React/API·DB·로그인과 CPI 한정 생성/검증 연결이 기록되어 있다. 이번 논의에서 해당 테스트를 다시 실행한 것은 아니다.
- [선정 사례](../verification/news/뉴스_선정_고정_사례.md)의 관련성·중요성·새 사실은 사전 검토된 입력이다. 일반 뉴스에서 이를 추출·검증하는 전체 경로가 완성된 것은 아니다. BLS CPI 시험을 Marketaux 제품 흐름 완료로 간주하지 않는다.

### 개발 전에 구체화할 설계

1. **일반 뉴스의 검증 책임**: AI가 추출할 정보, 코드가 기계적으로 확인할 정보, 운영자가 승인 시 대조할 의미를 명시한다. 현재 범용 의미 검증은 완료되지 않았다.
   - 추천: reviewed MVP에서 AI가 근거를 연결한 초안을 만들고 코드가 시각·필수 필드·수치 대응·중복·길이 등을 검사하며, 운영자가 근거 대비 의미·관련성·중요성을 최종 검토한다. 기계 검사 통과를 사실 정확성 보증으로 표시하지 않는다. auto 진입 조건은 별도로 유지한다.
   - 대안: 지원 사건 유형과 문형을 한정하고 유형별 검증기를 먼저 만든다. 자동 차단 범위는 설명하기 쉬우나 개발량이 늘고 기존의 폭넓은 뉴스 범위를 축소할 수 있다. 미지원 유형 처리도 정해야 한다.
2. **실제 뉴스 입력 계약**: Marketaux에서 사용할 필드·허용 근거·질의 범위·구성기업 기준 자료·누락/모호함 처리를 정한다. 검색/권한 검증 결과 없이 숫자 임계값이나 완전 수집을 확정하지 않는다.
3. **운영 복구 계약**: unknown/partial 원칙은 유지하고, CLI에서 받을 확인 자료·허용 상태 전이·권한·감사 이력을 명시한다. 자동 재전송이나 새로운 복구 화면을 추가하는 제안은 아니다.

### 사용자 선택과 외부 검증을 구분

Marketaux·지수의 이용 범위, 실제 검색 품질, X 인증/비용, AWS 메모리·도메인·백업 비용은 검증 과제다. 선호도 질문으로 통과 처리할 수 없다. 기존 정책대로 미충족 항목의 실제 운영은 보류하고 허용 입력·모의 전송으로 개발한다. 2주 목표와 공개 운영 합격은 구분한다.

### 관리자 화면 확장안 · 제안

기존 2화면의 뜻은 운영 요약과 후보 목록을 합친 대시보드, 그리고 근거·완성 글·검증·승인/보류·결과를 모은 편성 상세다. 최소 검토 흐름은 가능하지만 수집부터 발행까지의 운영 업무를 각각 살펴보는 구조는 약하다.

| 상위 메뉴 제안 | 업무·주요 표시 |
| --- | --- |
| 대시보드 | 오늘 AM/PM 진행·다음 발행·승인 대기·조치 필요·예산 요약 |
| 콘텐츠 검토 | 편성 목록과 상세, 게시 미리보기와 근거 비교, 검증 사유·승인/보류 |
| 수집 현황 | 지수·기사 조회, 출처·시각·수집 구간, 채택/제외/중복의 이유 |
| 발행 내역 | 편성별 성공·부분 성공·실패·결과 불명, 게시물 링크·버전·승인 이력 |
| 운영 현황 | 작업 실행 이력, 장애·Telegram 결과, 제공처별 사용량·예상 비용 |
| 설정 | 현재 편성·한도·모드·연결 상태 조회. 변경 가능한 항목은 별도 결정 |

- 6개 메뉴는 6개 화면과 같지 않다. 콘텐츠 검토 등의 목록·상세를 IA에서 나누고 로그인은 별도 진입 흐름으로 둔다. 설정은 우선순위를 낮출 수 있다.
- 대시보드는 요약과 작업 진입, 각 상세 메뉴는 원인·근거 확인에 집중한다. 검토 상세의 게시 미리보기/근거 좌우 비교, 실행 단계와 상태·시각 표시를 중심으로 시각 완성도를 높인다.
- 수집 현황에서 기사 하나를 조회하는 것과 편성 전체를 승인하는 것을 구분한다. 조회 화면 추가만으로 수동 수집·재생성·재게시 권한까지 추가하지 않는다.
- 문안 수정·재검증을 UI에 포함할지는 기존 CLI 전용 정책을 바꾸는 제품 결정이다. 포함 시 첫 전송 전 수정, 새 버전 생성·재검증·재승인 원칙을 유지하는 방향을 추천한다. API/시험/작업 시간은 WBS에서 재산정한다.
- 아직 메뉴 수·새 기능·일정 확대는 사용자 확정이 아니다. 기존 기준 문서의 일괄 재작성은 IA 논의 후 진행한다.

### 2주 가능성 검토와 기획 보완 목록 · 제안

사용자는 위 구성을 긍정적으로 평가하고 2주 내 가능 여부와 현재 기획의 수정·보완 목록을 요청했다. 이번에는 구현을 시작하지 않고 범위·우선순위를 제안한다.

- 기존 시간 기준은 2주 총 30시간이다. 초기 React/API/DB·인증·검토 UI는 재사용 가능하지만 일반 뉴스/AM 통합·worker·X·Telegram·AWS 연결과 인수 시험은 남아 있다.
- 파일 확인상 `src/xfolio/jobs/`는 없고 `src/xfolio/publish.py`는 모듈 설명만 있으며, `deploy/`의 기존 cloud 자산은 이전 시험용이다. 파일 확인은 현재 기능 전체의 재검증이 아니다.
- 6메뉴·웹 편집·실제 연동·AWS·장애 시험을 모두 30시간에 끝낼 수 있다고 보장하지 않는다. 6메뉴 중 신규 메뉴를 조회 중심으로 제한하고 입력/권한이 준비돼 있다면 2주 MVP에 도전할 수 있지만 여유가 작다.
- 읽기 중심 메뉴 확장·핵심 연동·문서/검증의 초기 작업량 가안은 약 35~50시간, 웹 편집·재검증까지 포함하면 약 40~60시간이다. 상세 WBS 전의 추정 범위로, 일정 확정이나 자동 코드 생성으로 검증 시간을 대체한다는 뜻이 아니다. 외부 승인/권한 대기와 5거래일 운영 관측은 별도다.
- 30시간을 유지하면 웹 편집·설정 변경·수동 재실행은 후속으로 분리하고, 뉴스 검토부터 발행 결과까지 이어지는 흐름과 조회 화면 완성도를 우선한다. 앞선 웹 편집 추천은 제품 경험 관점이었으며 30시간 제약에서는 우선순위를 낮춘다.
