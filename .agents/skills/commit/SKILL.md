# 작업별 커밋 승인

현재 변경을 검토 가능한 작업 단위로 나누고, 각 단위에 대한 사용자의 명시적 승인을 받은 뒤 해당 변경만 커밋한다. 이 스킬을 불러온 사실만으로 커밋 승인을 간주하지 않는다.

## 변경 확인과 제안

1. 저장소 루트, 현재 브랜치, `git status --short`를 확인한다. 추적 파일의 staged·unstaged diff와 untracked 파일 내용을 각각 검토한다. 변경 내용을 확인하지 못한 파일은 커밋 후보에 넣지 않는다.
2. 변경의 목적과 의존 관계를 바탕으로 커밋 후보를 묶는다. 한 목적의 변경은 가능한 한 함께 두고, 독립적인 목적은 분리한다. 요청 맥락과 기존 작업 기록이 있으면 분류에 활용하되, 근거가 불분명한 변경은 임의로 묶지 말고 사용자에게 확인한다.
3. 각 후보에 대해 포함 파일, 변경 요약, 제안 커밋 메시지를 한국어로 제시한다. 파일 일부만 관련되면 파일 전체를 후보로 삼지 말고 hunk 단위 분리를 검토한다. 실제 변경과 맞지 않는 범용 메시지는 제안하지 않는다.
4. 후보별로 승인 여부를 묻는다. 사용자가 특정 후보를 승인하거나 모두 승인한다고 명확히 말하기 전에는 `git add`, `git commit` 등 인덱스나 저장소 이력을 바꾸는 명령을 실행하지 않는다. 모호한 응답은 승인으로 처리하지 않는다.

## 승인된 후보 커밋

- 승인 직전에 상태와 diff를 다시 확인한다. 승인 후 내용이 바뀌었거나 새 변경이 생겨 후보 범위가 달라졌으면 해당 후보를 다시 제시하고 승인받는다.
- 승인된 후보에 속하는 변경만 포함한다. `git add .`나 `git add -A`로 후보 밖 변경을 끌어들이지 않는다. 부분 파일 변경은 필요한 hunk만 선택한다.
- 기존 staged 변경을 먼저 검토한다. 승인된 후보 밖의 변경이 인덱스에 있으면 함께 커밋하지 않는다. 기존 staged 내용을 보존하면서 후보만 안전하게 분리할 수 없으면 커밋을 멈추고 상황과 해결 선택지를 설명한다.
- 한 번에 여러 후보가 승인되어도 각 후보를 별도 커밋으로 만든다. 커밋 직전 staged diff가 승인된 후보와 일치하는지 확인한다.
- 커밋 후 `git status --short`와 최신 커밋 내용을 확인해 결과를 보고한다. 승인되지 않은 후보는 건드리지 않는다.
- `git push`는 요청에 포함되지 않는 한 실행하지 않는다. 저장소의 `AGENTS.md`와 사용자의 별도 지침이 더 엄격하면 그 지침을 따른다.

## 완료 보고

커밋한 후보별 해시와 메시지, 보류한 후보, 남은 작업 트리 변경을 간단히 보고한다. 커밋을 만들지 못했다면 이유와 필요한 다음 조치를 명시한다.
