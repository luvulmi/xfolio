Neon은 오래된 비교 문서의 0.5GB가 아니라 조회일의 가격·플랜 페이지에 표시된 **1GB**를 사용했다. CU-hours·전송량을 소진하면 다음 주기 또는 업그레이드까지 compute가 중단되며 한도 초과가 데이터 삭제를 뜻하지는 않는다. 무료 복원 이력은 최대 6시간 또는 변경량 한도가 적용되므로 장기 백업을 대체하지 않는다.

Streamlit은 로컬 전용 기술이 아니다. 현재 코드의 `sqlite3`·로컬 파일 접근을 PostgreSQL 저장 인터페이스로 바꿔야 한다. Community Cloud의 로컬 파일은 영속성을 보장하지 않으므로 SQLite 파일을 올리는 방식으로 운영 원장을 보존하지 않는다. [파일 영속성 공식 설명](https://docs.streamlit.io/develop/concepts/connections/connecting-to-data)

### PC를 끄고도 동작하는 흐름

```text
Cloud Scheduler → Cloud Run Jobs의 Python 수집·분석·게시 작업
                              ↕
                    Neon PostgreSQL 공통 기록
                              ↕
            Streamlit Community Cloud의 비공개 관리자
                              ↕
                       PC·휴대폰 브라우저
```

관리자에서 검토·승인 버전을 DB에 저장하고 별도 게시 작업이 검증·마감·한도를 다시 확인하는 기존 경계를 유지한다. 관리자 절전 중에도 별도 예약 작업은 실행될 수 있다. 비공개 접근 설정과 운영자 권한 검사는 구별하고, 관리자에는 게시용 비밀 키 대신 필요한 범위의 DB 접근 권한을 부여하는 설계를 우선한다. DB TLS·연결 복구·후보 버전 고유 제약·상태 점유·게시 성공 불명 처리는 후속 구현이다.

### 무료 계산 자원에 들어오는지 산술 확인

아래는 배포 실측이 아닌 보수적인 실행 횟수 예시다. 아침·기업 운영일 월 22일, `Asia/Seoul`, 각 실행의 **시작·종료·외부 API 대기를 포함한 청구 시간 60초**, 1 vCPU·1GiB·실행당 단일 task·플랫폼 자동 재시도 0을 가정한다.

| Scheduler 작업 | 빈도 예시 | 월 실행 |
| --- | --- | ---: |
| 수집·아침 준비의 공통 시작 | 07:00~17:30 매 30분, 22회/일. 아침·기업 처리는 현재 시각과 거래일로 분기 | 484 |
| 승인 게시 큐 확인 | 07:00~17:55 매 5분, 132회/일. 게시 허용 시간은 코드로 별도 검사 | 2,904 |
| 백업·보관 정리 | 30일 동안 하루 1회 | 30 |
| 합계 | 등록된 예약 3개 | **3,418** |

`3,418 × 60 = 205,080 vCPU-초`, `3,418 × 60 × 1GiB = 205,080 GiB-초`로 두 무료 한도보다 작다. 일별 운영 여부는 기존 운영 정책을 따르고 미국 거래일은 코드에서 판정한다. 실행이 1분보다 길거나 재시도·시험·다른 GCP 프로젝트가 같은 무료 몫을 쓰면 초과할 수 있다. 이 예시로 정시 실행이나 전체 청구 0원을 보장하지 않는다.

Neon은 0.25 CU에서 하루 11시간·22일 내내 활성화됐다고 가정하면 약 **60.5 CU-hours**다. 야간 백업·운영자 추가 조회·브랜치·규모 증가분은 별도다. 24시간 계속 쿼리를 보내면 30일에 180 CU-hours로 무료 몫을 넘기므로 야간의 불필요한 polling과 관리자 자동 갱신을 피한다.

### 월 $0 목표에 함께 계산할 항목

GCP는 **활성 결제 계정이 필요하고, 무료 한도 초과·대상 외 서비스는 과금**된다. 기간 한정 $300 체험 크레딧을 계속 무료인 근거로 계산하지 않는다. [Free Tier 조건](https://docs.cloud.google.com/free/docs/free-cloud-features)

- Artifact Registry 무료 저장은 0.5GB다. Python 이미지와 여러 revision의 총 저장량·정리 정책을 확인해야 한다. Cloud Build·로그·외부 전송·백업 저장도 별도 사용량이다.
- Secret Manager는 활성 버전 6개·접근 10,000회/월이 무료다. 작업 3,418회에 매번 비밀 4개를 읽으면 13,672회로 초과한다. 모든 polling에서 모든 키를 읽지 않고 실제 처리 단계에 필요한 키만 읽는 설계와 실제 접근 과금 확인이 필요하다. 비용 절감을 이유로 키를 Git·이미지·로그에 넣지 않는다.
- Cloud Run의 인터넷 전송 무료 조건은 지역에 따라 확인해야 하며 가격표는 북미 내 1GiB 무료를 명시한다. 미국 리전의 DB·작업을 우선 비교하되 실제 연결 경로·전송량으로 계산한다.
- 일반 alerts-only 예산은 자동 중단이 아니다. 별도 spend cap 지원·적용 범위와 실행 수·timeout·재시도·이미지 보관 제한을 배포 전에 확인한다.

### 선택 뒤 필요한 변경·검증

## 조사 결론

확정 결정: 사용자가 **현재 Windows PC에서만 접속**하는 구성을 선택했다. Streamlit은 `127.0.0.1:8501`, SQLite는 같은 PC의 `data/xfolio.sqlite3`를 사용한다. 로컬 단일 사용자 구성으로 공개 URL·원격 접속·라우터 포트 전달·클라우드·OIDC는 이번 범위에 넣지 않는다. [현재 비용 구성](월_비용.md)을 따르며 아래 Linux VM·관리형 DB 비교는 조사 이력이다.

첫 버전은 **현재 Windows PC에 SQLite·로컬 Streamlit·작업 스케줄러를 함께 두는 구성**으로 확정했다. 유료 VM 없이 동일 호스트의 공통 기록을 사용한다. Python 3.12의 `sqlite3`로 DB 접근을 모으고, 화면과 예약 CLI는 별도 프로세스로 실행한다. 브라우저 세션에 수집·게시 타이머를 넣지 않는다. 현재 가상 preview CLI·가상 초안 저장·조회·UI를 구현/검증 중이며 실제 승인·앱 로그인·게시·백업과 로그온 시작 작업 등록은 미구현이다.

## 로컬 관리자 화면의 확정 배치

| 항목 | 확정 기준 | 현재 상태 |
| --- | --- | --- |
| 접속 | 같은 Windows PC에서 `http://127.0.0.1:8501` | 로컬 가상 미리보기 코드 구현/검증 중. 원격 접속 제공 안 함 |
| 사용자 | 해당 PC의 단일 운영자·Windows 사용자 세션 | 현재 가상 화면에는 앱 로그인이 없음. 실제 근거 조회·승인에는 R11의 인증·운영자 권한 검증을 연결한 뒤 활성화 |
| 서버 시작 | Windows 로그온 시 시작을 제품 등록 전 계획으로 두고 그전에는 수동 실행 | 작업 스케줄러 등록·서버 자동 시작 시험 미실행 |
| 공통 기록 | 프로젝트의 `data/xfolio.sqlite3` | `preview_drafts`의 가상 문안·가상 근거·버전·보류 이유만 저장 |
| 화면 기능 | 가상2글·뉴스0건1글·부분 수집 보류, 가상 저장·기존 버전 조회 | 실제 승인 버튼·X 전송·실기사 AI 없음. `can_publish=False` |
| 운영 확장 | 실제 승인·게시 상태와 권한·백업·복원은 후속 계약과 시험으로 연결 | 현재 가상 DB를 운영 승인·발행 원장 완성으로 취급하지 않음 |

수동 실행 형식은 저장소 루트 기준 다음과 같다. 이 문서 조사에서 서버를 시작하거나 설정 파일을 바꾸지는 않았다.

```powershell
uv run --extra dashboard streamlit run dashboard/app.py --server.address 127.0.0.1 --server.port 8501 --server.headless true
```

`server.address`는 서버의 수신 주소, `server.port`는 포트이며 `headless=true`는 서버 시작 시 브라우저 자동 열기를 막는다. `browser.serverAddress`만 바꾸는 것을 로컬 바인딩과 혼동하지 않는다. 운영자는 필요한 때 직접 주소를 열고, 화면을 닫아도 향후 예약 CLI는 별도로 실행되도록 설계한다. [Streamlit 설정](https://docs.streamlit.io/develop/api-reference/configuration/config.toml)

로그온 시작은 특정 운영자 `LogonTrigger`와 프로젝트 경로를 쓰는 등록 전 계획이다. 같은 PC 접근 선택이 PC 전원·사용자 세션·인터넷의 상시 가용성을 보장하지 않는다. 로그아웃 중 무인 실행과 절전 복귀는 [Windows 실행 계약](예약_실행.md#확정한-자동화-방식과-등록-전-실행-설계)의 후속 시험이다. [Microsoft LogonTrigger](https://learn.microsoft.com/en-us/windows/win32/taskschd/logontrigger)

현재 실기사 응답의 본문·description·snippet은 이 DB에 저장하지 않는다. 이용 조건 확인 전 외부 AI 입력·실기사 근거30일/백업·공개 게시로 연결하지 않으며 가상 fixture의 근거 부분 문자열 대조를 자동 의미 검증으로 표시하지 않는다. X 가중 길이도 참고값이고 게시 가능 승인과 구분한다. [미리보기 계약](../../tasks/verification/뉴스_수집과_아침_미리보기.md) · [데이터 이용 조건](데이터_이용_조건.md)

사이트와 작업을 서로 다른 호스팅에 배치한다면 SQLite 파일 공유 대신 Supabase PostgreSQL 같은 원격 DB를 사용한다. 무료 DB는 가능하지만 휴면·백업·연결 설정을 추가로 관리해야 한다. [Python sqlite3 문서](https://docs.python.org/3.12/library/sqlite3.html), [SQLite 적합한 용도](https://www.sqlite.org/whentouse.html)

## 후속 승인·게시 연결의 목표 흐름

```text
수집·AI 작업 → 공통 DB의 근거·후보 버전·검증 결과
                         ↓
                  Streamlit 운영자 검토
                         ↓
               승인 버전·일일 한도 예약 저장
                         ↓
              게시 작업이 승인 상태를 다시 확인
                         ↓
                 X 결과·게시물 ID 기록
```

위는 reviewed 모드의 후속 목표이며 현재 가상 미리보기의 구현 범위가 아니다. 화면은 Streamlit으로 후보 문안·출처·시각·검증·승인/보류·게시 결과·마지막 실행·비용을 보여 주고 승인 상태만 DB에 기록하도록 연결할 계획이다. 안정화 후 auto에서는 화면의 건별 승인 없이 코드의 검증·예약 상태로 처리한다. 화면 버튼에서 X를 직접 실행하지 않으며 DB 제품이 정확성을 자동 보장하지 않으므로 아래 로직이 필요하다.

- 기사·사건·근거 버전, 초안 버전, 승인자·승인 시각, 발행 건·글 순서·X ID, 실행·비용 기록을 분리한다.
- 고정 후보 버전을 조건으로 승인하고, 같은 발행 키의 중복 생성을 DB 고유 제약으로 막는다.
- 승인 예약·한도 검사·게시 작업 점유는 짧은 트랜잭션으로 처리한다. 외부 API 응답을 기다리는 동안 DB 쓰기 잠금을 유지하지 않는다.
- 전송 전 상태와 응답 후 ID를 각각 기록한다. 중간 종료는 성공 불명으로 보존하고 재전송하지 않는다. DB 트랜잭션과 X 전송을 하나의 원자적 작업으로 만들 수 있다고 보지 않는다.

## SQLite 운용 조건

Streamlit과 작업은 같은 서버의 지속 디스크에 접근한다. GitHub Actions가 파일을 내려받아 수정한 뒤 다시 업로드하는 방식, 네트워크 공유 폴더에 WAL DB를 놓는 방식은 채택하지 않는다. WAL은 같은 호스트의 프로세스 사용이 전제다. [SQLite WAL](https://www.sqlite.org/wal.html)

단일 게시 작업을 기본으로 하고, 쓰기 경합 시 제한된 대기·재시도 및 실패 기록을 둔다. DB 연결을 화면 사용자 사이에서 무분별하게 공유하지 않는다. 서버가 늘어나거나 동시 쓰기가 커지면 PostgreSQL로 이전하는 것이 다음 선택이다. 현재 규모에 충분하다는 성능 측정은 아직 없다.

백업은 실행 중인 `.db` 파일만 단순 복사하지 않고 Python `Connection.backup()` 또는 SQLite Online Backup API로 일관된 사본을 만든다. 일일 백업을 서버 밖에도 보관하고, 빈 DB에 실제 복원해 승인·발행 키·게시물 ID를 확인한다. 서버 스냅샷은 보조 수단이며 애플리케이션의 백업·복원 시험을 대신하지 않는다. [Python backup](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Connection.backup), [SQLite Online Backup](https://www.sqlite.org/backup.html)

Supabase Free를 택하면 CLI `db dump` 등의 자체 외부 백업을 예약해야 한다. Supabase DB 백업에는 Storage API로 넣은 실제 파일이 포함되지 않으므로 근거 파일을 별도 저장할 경우 별도로 보존한다. [Supabase 백업](https://supabase.com/docs/guides/platform/backups)

## 원격 접속을 검토할 때의 로그인 대안 · 이번 범위 제외

다음 OIDC·Community Cloud 조사는 이전 원격 배치 대안이다. 현재 선택은 Windows PC에서만 접속하는 단일 사용자 화면이며 별도 앱 로그인·OIDC·외부 호스팅을 이번 구현에 추가하지 않는다. 향후 원격 접속 범위를 바꾸려면 실제 승인 기능의 권한과 함께 다시 설계한다.

실제 관리자 기능은 [운영 정책 R11](../운영_정책.md)의 인증·운영자 권한 검증·세션 만료·후보 버전 검사 후 활성화한다. Windows 사용자 세션과 앱의 승인 권한은 별도로 검사해야 한다. 현재 로그인 없는 화면은 가상 자료의 미리보기/저장 단계에 한정하며 실제 기사 근거·승인 기능을 제공하지 않는다. 로컬 운영자 로그인 방식은 실제 승인 연결 시 구현하고 OIDC 도입은 별도 선택이다.

Streamlit은 OIDC 로그인용 `st.login()`, 사용자 정보 `st.user`, 로그아웃 `st.logout()`을 제공한다. Google Identity 등 제공처의 앱 등록·redirect URI·client ID·secret·cookie secret 설정이 필요하다. **로그인 성공과 운영자 권한은 구별**하며 서버에서 허용된 계정의 issuer·subject를 확인한 뒤 근거 조회와 상태 변경을 허용한다. 사이트 로그인으로 X API 권한이 생기는 것은 아니다. [Streamlit 인증](https://docs.streamlit.io/develop/concepts/connections/authentication)

이 문서의 쿠키 만료 기본값은 30일이며 제공처 토큰 만료와 직접 연결되지 않는다. 필요 시 토큰의 만료를 별도로 확인해야 한다. 승인 요청마다 로그인·허용 계정·후보 버전을 재검사하고, 인증 비밀은 저장소 밖에 둔다. OIDC 제공처 계정·요금·등록 가능성은 실제 연동 전에 확인한다. [Streamlit 인증](https://docs.streamlit.io/develop/concepts/connections/authentication)

Streamlit Community Cloud는 12시간 방문이 없는 앱을 휴면 처리한다. 따라서 무료 사이트를 곧바로 상시 작업 서버로 사용하지 않는다. 별도 외부 DB와 스케줄러를 연결하는 경우 관리 화면 용도로는 검토할 수 있지만, 재시작 후 로컬 파일 보존을 운영 DB의 계약으로 삼지 않는다. [Community Cloud 관리](https://docs.streamlit.io/deploy/streamlit-community-cloud/manage-your-app)

## 비용 입력과 남은 확인

- SQLite 자체 DB 구독액은 $0 추가, VM·백업 비용은 [R7](예약_실행.md)에서 합산한다. 호스팅 비용을 다시 DB 항목에 중복 더하지 않는다.
- Supabase Free는 현재 포함량 안에서 $0이지만 백업 저장·작업 호스팅·OIDC 제공처 비용까지 $0으로 확인한 것은 아니다.
- Supabase Pro는 기본 $25부터이며 세금·환율·초과량은 별도다. 전체 월 비용에서 무료안과 유료안을 따로 계산한다.
- 현재 남은 확인은 가상 DB·UI 연결, 실제 뉴스 저장 가능 조건, 운영 DB 스키마·백업/복원, 동시 승인/게시 경합, Windows 로그온·중단 후 복구다. 1GB VM 메모리와 OIDC 로그인 시험은 원격 배치 대안의 이력이며 현재 필수 작업이 아니다.

10/22 문서 조사 당시 DB·사이트를 새로 생성하거나 키를 확인하지 않았다. 현재 가상 초안 저장 코드와 당시 임시 DB 실험을 구분하며 서비스별 보관 가능 용량이 기사 전문 저장 권한을 뜻하지 않는다.

## 후속 확인: 현재 Windows PC와 SQLite 실험

10/22에는 `127.0.0.1` 로컬 접근을 제안했고10/24 사용자가 현재 PC에서만 접속하는 구성으로 확정했다. 공용 IP·포트 전달·터널·외부 호스팅은 도입하지 않는다. 사용자별 데이터 폴더와 DB 파일 권한을 제한하고 Git에 넣지 않는다. 당시 SQLite 실험에서는 화면이나 네트워크 서버를 실행하지 않았다. 현재 가상 UI 코드·검증 진행과 실제 서버 배포·로그온 작업 등록을 구분한다.

2026-10-22 당시 `.venv`의 `importlib.util.find_spec` 확인 결과는 `streamlit=False`, `authlib=False`였다. 이는 과거 환경 관측이며 현재 설치 상태를 대신하지 않는다. `pyproject.toml`의 `dashboard = ["streamlit"]` 선언만으로 실행·로그인 완료라고 판단하지 않는다. 향후 OIDC를 도입한다면 공식 `st.login`의 Authlib 의존성과 별도 계정 등록을 확인해야 하지만 이번 로컬 구성에는 추가하지 않는다. 이번 문서 작업에서 의존성·설정을 바꾸거나 OIDC 계정을 등록하지 않았다. [Streamlit st.login](https://docs.streamlit.io/develop/api-reference/user/st.login)

SQLite의 중복 키·승인 버전·롤백·백업 복원 실험의 상세 결과와 재현 명령은 [기술 조사 후속 검증](../../tasks/verification/기술_조사_후속_검증.md#sqlite-기능-시험-상세)에 모았다. 실제 앱 상태 관리·강제 종료·운영 백업·X 전송 검증은 남아 있다.
