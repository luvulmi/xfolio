## 확정한 게시 모드

| 모드 | 처리 | 외부 게시 조건 |
| --- | --- | --- |
| dry_run | 수집·생성·검증·미리보기 | X 전송 없음 |

개발은 dry_run→reviewed 순서로 진행하고, R14의 연속5거래일·장애·중복·마감·복구 검증 뒤 auto로 전환한다. 관리자 사이트는 auto에서도 근거·보류·게시 결과를 보여 주며 정상 건별 접속을 요구하지 않는다. 아래 승인·재승인·미승인 차단 절차는 reviewed 전용이고 auto에서는 현재 버전의 검증 통과·재검증을 적용한다. 숫자/사실 오류·중복·한도 위반 같은 중대한 결함은 자동 게시를 중단하고 reviewed로 돌아가 수정·시험한다.

지수 수집은 yfinance로 확정했다. 수집의 구현 계약은 [지수 종가 검증](../tasks/verification/market/지수_종가_조회.md)에 두고 실제 오전 관측은 [오전 도착 시험](../tasks/verification/market/지수_오전_도착.md)에 기록한다. 게시 모드의 구현 완료를 뜻하지 않는다.

## R01. 시간 필드·기준 전 버전

- 내부 시간은 UTC로 저장하고 운영 화면·게시문은 KST로 표시한다. 미국 거래일은 거래소 현지 날짜로 별도 기록하며 서머타임을 고정 시차로 계산하지 않는다.
- 원문 최초 발행, 수정, 수집 완료, 사건 발생, 적용일·실적 대상 기간을 구분한다. 출처의 원래 시간대와 시간 정밀도도 보존한다.
- 신뢰 가능한 기관 발행 시각 또는 SEC 접수 시각과 시간대가 필요하다. 날짜만 제공되는 자료는 초기 지원에서 보류하고 사유를 남긴다. 수집 시각을 발행 시각으로 대체하지 않는다.
- 수정 시각이 없어도 기준 전 확보한 허용 본문·요약 버전과 수집 완료 시각이 있으면 사용할 수 있다. 기준 후 처음 확보한 자료 버전은 과거 호에 소급 사용하지 않는다. available_at은 해당 버전의 실제 최초 확보 완료 시각이다. 요청 시작 시각만 기준 전인 것은 충분하지 않다.
- 아침 수집 준비는 07:00 시작, 기준 전 자료 확보는 07:30까지, 초안 준비는 07:45 목표로 잡는다. 이후 재조회는 기준 전 확보한 버전의 유효성 대조에만 사용하며 새로운 근거/본문으로 교체하지 않는다. 실제 예약 정밀도·제공처 지연은 조사에서 확인한다.

## R02. 뉴스 확인·이월의 단순 기준

- 아침 호는 직전 아침 호의 정보 기준 이후~이번 호 07:30에 확인할 수 있는 세 지수 관련 뉴스를 검토한다. 추가 뉴스는 07:30 이후 낮 감시에서 후보를 모아 18시 편성에 사용한다. 17:30까지 발행된 기사, 최종 수집/근거 동결 17:45까지를 MVP 기준으로 둔다. 겹치는 조회 창으로 지연 수록 기사를 찾되 기사·사건 ID와 마지막 완료 커서로 중복을 막는다. 조회 시작점·겹침 폭은 실제 질의의 검증값을 설정한다.
- 최초 실행·장애 복구의 최근 7일 조회 상한은 유지한다. 이는 빠진 기사를 찾는 범위이며, 그 안의 모든 기사를 게시한다는 뜻은 아니다.
- 게시 가능 기간을 별도의 72시간 같은 숫자로 제한하지 않는다. 아직 전달하지 않은 중요한 새 사실인지, 현재 독자에게 의미가 있는지, 출처·시각·근거가 명확한지를 게시 전에 판단한다. 오래된 발표를 새 소식처럼 쓰지 않고 필요한 경우 공개일을 표시한다.
- 같은 사건의 재인용은 게시하지 않는다. 중요한 새 사실·정정이 있는 후속은 다음 선정 회차에서 재검토한다. 이월만으로 자동 게시하지 않으며 중복·근거·중요도·승인을 다시 확인한다.
- 단순 재인용·재해설은 새 사실로 세지 않는다. 한도 소진·승인 만료로 넘어간 후보도 다음 기회에 새로 검토하고 승인한다.

## R03. 사건 식별·후속 보도·선정 설명

- 같은 URL/기관 원자료 ID와 같은 사건을 별도로 판정한다. 사건은 주체 + 사건 유형 + 발표 회차/대상 기간 + 거래·정책 식별 정보로 묶는다. 실적 분기가 다르면 별도 사건이며 같은 분기의 재인용·수정은 후속이다.
- 한 실적 발표에 포함된 매출·이익·회사 전망은 한 사건으로 묶는다. 동일 인수 거래의 승인·조건 변경·완료도 후속으로 묶는다. 서로 다른 독립 거래는 별도 사건으로 둘 수 있다.
- 여기서 회사 전망은 회사가 공식 발표한 가이던스의 내용·변경 사실이다. 미래 실적의 실현을 단정하지 않는다. 분석가 예상·주가 전망·목표가를 독립 뉴스로 선정하지 않는다. [선정 고정 사례](../tasks/verification/news/뉴스_선정_고정_사례.md)
- 같은 사건 후보는 하나만 두고 복수 근거를 연결한다. 대표 기사는 검증에 충분한 근거 → 적법하게 사용할 수 있는 최신 버전 → 안정적인 기사 ID 순으로 고른다. 기관 발표ID·SEC accession은 자료 식별자이며 동일 사건의 여러 문서/첨부를 별도 뉴스로 세지 않는다.
- 후속으로 발견한 새 사실은 이미 승인한 본문에 자동 합치지 않고 다음 선정 회차에서 재검토한다. 이미 승인한 원문 사실을 무효화하는 정정·충돌은 후보를 즉시 보류한다.
- 아침·추가 후보 모두 세 지수 관련성·확정된 사건 중요성 → 영향 범위 → 새 사실 시각 → 안정적인 ID 순서를 따른다. AI에는 근거와 순위 이유를 요구하고 근거 없는 수치 점수를 붙이지 않는다.
- 사건 중요성 설명에는 변화 대상·기간·규모·사업 범위를 담는다. 단위가 다른 규모를 비교할 수 없으면 동급으로 두고 다음 기준을 적용한다. 판단이 모호한 중복·핵심 사건은 운영자 검토 전 발행하지 않는다.

## R04. 공식 자료·감시 기업·관련성

- 수집은 Fed·BLS·BEA 공식 발표와 SEC 주요 기업 10개로 제한한다. Marketaux/언론 뉴스 검색은 운영 경로에서 제외한다. 관련 지수는 S&P500·Nasdaq-100·DJIA다.
- watchlist_version·CIK·기업명/티커·선정 이유·참조/확인일·활성시점을 서버 설정에 보존한다. 기업 구성은 확정했으며 공식 법인명·CIK·감시 시작일은 검증 대기이며 설정 UI는 읽기 전용이다. 여러 티커가 같은CIK면 한 기업으로 센다.
- 실적·인수합병·정책·경제지표의 확정된 발표 사실을 고른다. 회사 이름·지수 편입만으로 중요성을 통과시키지 않는다. 공식 회사 전망은 발표 사실로만 표현한다.
- 수집 완주는 기관/지표/CIK/문서유형·조회창 기준이다. complete+신규0건, partial, failed와 자료별 unsupported/rights차단을 구분한다. 필수 scope 실패 또는 중요한 사건의 필수 근거 충돌은 해당 편성 보류다.
- 커서는 scope별 완주 때만 전진한다. 수정 공시/발표는 자료와 사실 버전을 갱신하며 기존 승인 내용을 무기록 덮어쓰지 않는다. 상세 호출/시간/중복 계약은 [수집 설계](specifications/공식_발표와_공시_수집_설계.md)를 따른다.

## R05. reviewed 승인·발행 시점·철회

- 2026-10-28 상세 확정: 사용자의 추천안 진행 위임에 따라 아침 최대 3글·저녁 최대 2글은 각각 한 편성 버전으로 일괄 승인한다. 기사별 승인·부분 승인은 MVP에 넣지 않는다. 저녁 정상 0건은 실행 결과만 남기고 승인/발행 job을 만들지 않는다. 아래 수동 새 버전 절차도 같은 범위를 따른다.
- 잘못된 초안은 `hold`로 전체 보류한 뒤 CLI로 기존 동결 근거의 문안 수정·기사 제외만 수행한다. 게시문·순서·해시가 고정된 새 버전은 기존 승인을 무효화하고 모든 검증과 재승인을 요구한다. 지수 필수 글은 제외할 수 없다. 새 버전 생성과 기존 job 철회·예약 해제는 하나의 트랜잭션으로 처리하며 첫 외부 전송 시도 전까지만 가능하다.
- PM은 17:45까지 확보한 근거·후보를 고정한다. 이후 새 기사·사실·근거 추가는 다음 회차에서 재검토한다. 문안 수정·기사 제외도 기존 근거 안에서만 마감 전 허용한다. 게시 직전 재조회는 승인된 사실의 유효성 확인에만 쓰고 핵심 정정·충돌은 전체 편성을 보류한다. 교정 근거를 추가해 같은 저녁 호를 다시 만드는 예외는 두지 않는다.

- 승인 대상은 게시문 전체, 글 순서, 근거 버전, 지수 값, 대상 계정·편성·발행 날짜가 고정된 한 후보 버전이다. 승인자·시각·버전 식별자를 저장한다.
- 아침은 08:00 전 승인하면 08:00 발행 목표, 이후 승인하면 09:00 전 다음 게시 작업에서 처리한다. 07:45는 검토 준비 목표이며 승인 마감은 아니다.
- 추가 뉴스는 운영일 09:00~17:00 매시간과 17:30 최종 확인, 하루 10회 수집을 MVP 설정으로 둔다. 발견 즉시 게시하지 않는다. 마지막 필수 수집을 17:45까지 완주하고 근거·중요도·중복을 통과한 최대 2사건을 동결한다. 조회량 적합성은 별도 검증하며 부분 수집을 완주로 세지 않는다.
- 저녁 발행 목표는 **18:00**, 정상 검토 준비와 17:55 승인 완료 시 18:00~18:05 첫 요청을 시험 목표로 둔다. **18:10부터 신규 전송·자동 재시도 금지**는 두 글 순차 전송과 제한 복구를 위한 MVP 마감값이다. 별도 5분 승인 대기 Job은 제거하고 단일 worker가 발행 창에서만 60초마다 due 작업을 확인한다. 늦은 승인도 마감 내에만 처리하고 auto는 같은 시간·한도를 적용한다.
- 아침은 새로운 완료 미국 거래일당 1호, 저녁은 KST 날짜와 같은 날짜가 미국 거래일인 운영일에만 실행한다. 달력으로 휴장·서머타임을 판단하며 요일만으로 대체하지 않는다.
- 승인 직후 추가 뉴스의 남은 일일 한도를 원자적으로 예약한다. 한도가 없으면 승인 가능한 상태로 전환하지 않고 다음 검토로 넘긴다. 실제 게시·성공 불명 예약과 단순 승인 예약을 구별한다.
- 저녁 2건의 편성에서 예약 가능한 한도가 1건뿐이면 전체 승인을 거절한다. 일부만 승인하지 않는다. 최초 전송 전 편성 job은 하나를 유지하며 새 버전 생성 시 기존 승인을 철회하고 예약을 해제해 현재 버전 참조를 원자적으로 교체한다. 새 버전은 검증·재승인 때 전체량을 다시 예약한다. 과거 버전·결정 감사 기록은 보존한다.
- 게시 직전 승인 버전·마감·새 사실과 현재 관련성·중복·한도·근거 무효화·예산을 검사한다. 승인 후 원문을 재조회할 수 없으면 신규 게시를 보류한다. 기준 후 무관한 새 사실은 승인 내용을 바꾸지 않으며 핵심 정정·충돌만 기존 승인을 무효화한다.
- 게시문·근거·숫자·순서가 바뀌거나 보류·재생성이 발생하면 승인을 해제한다. 다음 날짜로 승인을 이월하지 않는다. 첫 전송 전 철회는 허용하고 예약을 해제한다. 전송 시작 뒤에는 미전송 글을 중단하되 전송한 요청을 취소한 것으로 간주하지 않는다.

- `hold`는 승인 전 보류와 전송 전 승인 철회에 공통 사용한다. 전송 시작 뒤에는 잔여 글 중단만 기록하고 이미 전송한 글의 결과·사건/비용 예약을 보존한다. 첫 전송 시도 후 새 버전 교체·재승인으로 우회 전송하지 않는다. 보류된 같은 버전은 다시 승인하지 않고, 허용되는 보류 사유를 해결한 새 버전의 검증·재승인을 요구한다. 구버전·만료·정정충돌 버전과 과거 승인 요청 재전송으로 상태를 되돌리지 않는다.

## R06. 대기열·저장·동시 실행

- 모드별 상태를 분리한다. reviewed는 검증 대기→승인 대기→승인/예약→게시 중→완료, auto는 검증 대기→검증 통과/자동 발행 대기→예약→게시 중→완료다. auto에서는 승인 대기에서 멈추지 않으며 한도 예약은 검증된 발행 건을 큐에 넣을 때 처리한다. 수정 버전은 reviewed 재승인 또는 auto 재검증 후 진행한다.

- 모드에 맞는 상태 외에 보류·만료·부분 게시·성공 불명을 별도로 둔다. 상태 사유·승인/검증 버전·변경 이력을 남긴다.
- 승인 대기 후보는 현재 중요도 순으로 다시 정렬할 수 있다. 승인된 후보는 새 후보가 왔다는 이유로 자동 교체하지 않는다. 운영자가 철회하고 다른 후보를 승인해야 한다.
- 아침 후보는 09:00, 저녁 후보는 18:10에 해당 날짜의 승인이 만료된다. 저녁은 18:00 전 전송하지 않는다. 이전 호 자체는 재발행하지 않고 뉴스의 새로운 사실만 다음 후보로 검토한다.
- 한도 예약·중복 확인·전송 시작 상태를 하나의 영속적 처리로 묶는다. 아침은 미국 거래일+편성, 추가 뉴스는 사건+새 사실 버전+발행 건을 안정적인 키로 사용한다. 시험·실제 게시 기록을 분리한다.
- 첫 요청 전에 발행 건을 저장하고 각 글의 결과·게시물 ID를 즉시 기록한다. 요청 중 프로세스가 종료되면 성공 불명으로 복구한다. 재시작·중복 스케줄러가 재시도 횟수나 한도를 초기화하지 않는다.
- 현재 제품 DB는 PostgreSQL이며 SQLite는 기존 개발/시험 자산이다. AWS의 API와 단일 worker는 공통 DB를 사용한다. 잠금·원자적 상태 점유·outbox의 운영 구현은 후속 검증하며 영속 저장을 지원하지 못하는 배포안은 제외한다.

## R07. 정상 수집·부분 누락·진행 기록

- 정의한 시간 구간·질의·페이지를 모두 확인한 경우에만 완전 수집으로 판정한다. 응답 잘림·페이지 누락·쿼터 중단·필수 질의 실패는 불완전 수집이다. 제공처 전체 시장 보도 완전성을 보장한다는 뜻은 아니다.
- 불완전 수집이면 그 회차의 아침 호 또는 추가 뉴스 신규 발행을 보류한다. 0건 정상 수집으로 표시하지 않는다. 이미 수집한 자료는 허용 범위 안에서 재사용하고 빠진 구간을 복구한다.
- 완전 수집 후 개별 자료만 근거가 부족하면 해당 자료를 제외하되, 중요한 사건의 필수 근거를 확인하지 못하면 R04에 따라 편성을 보류한다. 정상 제외 뒤 적격 뉴스가 0건이면 범위를 한정한 뉴스 0건 아침 호를 허용한다. 추가 뉴스 0건은 게시하지 않는다.
- 수집 성공 시점과 실제 게시 성공 시점을 별도로 기록한다. 승인·게시 실패가 수집 진행 기록을 되돌리거나 미게시 사건을 삭제하지 않게 한다.
- 복구 조회에서 7일을 넘는 공백은 누락 구간으로 남긴다. 수집이 중단됐던 사실을 감추기 위해 마지막 성공 시각을 현재로 옮기지 않는다.

## R08. 지수 숫자·반올림·수정치

- 정확한 세 지수의 같은 미국 거래일 마감 종가와 전 거래일 대비 등락률을 원문에서 확인한다. 직전 거래일 종가는 확보 가능할 때 같은 계열로 대조한다. 거래소 달력·마감 자료 여부·출처가 불명확하면 아침 호를 보류한다. ETF·선물·다른 지수로 대체하지 않는다.
- yfinance에서 `auto_adjust=False`의 일별 `Close`로 최근 완료 미국 거래일과 직전 거래일 종가를 조회하고 `(이번 종가 / 직전 거래일 종가 - 1) × 100`을 코드로 계산한다. 원본 정밀도를 보존하고 종가·등락률은 소수 둘째 자리, 반올림은 십진 HALF_UP으로 통일한다. 반올림 후 음의0은 0.00으로 표시한다.
- 심볼·거래일·필수 종가·계산값이 불명확하거나 충돌하면 기준일·계열·수정치를 확인할 때까지 보류한다. 결측·이전 날짜 값·미완료 거래일·검색 요약으로 수치를 채우지 않는다. 기존 검색안의 전 거래일 종가 없는 등락률 추출 예외는 현재 yfinance 경로에 적용하지 않는다.
- 기준 전 값이 오류였다는 정정이 게시 전에 확인되면 승인 해제 후 새 근거로 재검증한다. 아침 뉴스의 07:30 기준은 유지하고 지수 수정치의 확인 시각은 별도 표시한다. 게시 후에는 수동 정정한다.
- 기업·경제 뉴스의 수치는 원문 단위·기간·비교 기준을 유지하며 자동 환산·추정은 하지 않는다. 원문에 없는 예상치 대비 차이를 만들지 않는다.

## R09. 게시 형식·길이 초과

- 아침은 최대 3개 글: S&P 500·Nasdaq-100·DJIA 세 지수의 마감 종가·등락률 요약 1개 → Fed·BLS·BEA·SEC에서 확인한 중요 발표·공시 최대 2건을 중요도순으로 각각 설명·출처명·원문 링크와 함께 1글씩 게시한다. 확인된 변화의 주체·내용·시점과 필요한 조건을 설명하며 반복되는 AI 총평과 독립된 출처 모음 글은 생략한다. 뉴스 2건은 서로 다른 사건이어야 하고 이후 추가 뉴스와 중복 게시하지 않는다.
- 정상 수집 후 적격 뉴스가 0건이면 이번 수집 범위에서 선정 뉴스가 없음을 지수 글에 표시하고 1개 글로 발행한다. 수집 실패·불완전 수집·필수 지수 누락은 정상 0건으로 표시하지 않고 아침 전체를 보류한다.
- 추가 뉴스는 **18시 편성에서 KST 하루 최대 2건**, 한 사건당 독립된 글 1개로 제한한다. 한 실적 발표의 매출·이익·전망을 나누어 2건으로 세지 않는다. 모든 글은 280 가중 글자 한도를 적용하고 NFC·URL·이모지를 포함한 실제 가중 계산 규칙으로 완성본을 검사한다. 한글은 보통 2, 인식된 URL은 23으로 계산하며 계정·API에서 실제 전송 가능 여부는 후속 검증한다. [X 공식 글자 수](https://docs.x.com/fundamentals/counting-characters)
- 추가 뉴스 한도는 KST 날짜별로 계산하고 00:00에 새 날짜의 한도를 적용하되 이력은 보존한다. 게시된 건과 성공 불명·승인/자동 발행 예약 건의 합계가 2건을 넘지 않도록 원자적으로 예약한다. 일부라도 게시되면 1건을 사용하며, 확실한 미게시·전송 전 철회만 예약을 해제한다. 같은 발행 건의 재시도는 추가 차감하지 않는다.
- 아침·저녁 뉴스의 각 최대 2건은 의무 발행량이 아니다. 근거·중요도를 통과한 사건만 선정한다. 아침 후보를 단순히 미선정했다는 이유로 저녁 편성에 자동 이월하지 않는다. 중요한 새 사실이 있으면 새 후보로 검토한다.
- 지수 글에는 미국 거래일·두 종가·등락률·출처, 기사 글에는 주체·핵심 변화·사건 시점/기간·필요한 단위·조건·출처명·원문 링크를 남긴다. 정보 기준과 실제 게시 시각은 발행 단위에 남긴다. 뉴스 글 자체에서도 어떤 사건인지 식별할 수 있게 한다.
- 길이 초과 시 반복 문구·부가 해설 → 중요도가 낮은 부가 수치 순으로 줄인다. 핵심 숫자의 단위·기간·부정/조건 표현·출처를 임의 절단하지 않는다.
- 그래도 아침 뉴스가 원문 링크와 함께 한 글에 들어가지 않으면 해당 뉴스만 제외하고 다음 순위 후보로 대체한다. 적격 후보가 없으면 정상 수집 후 뉴스 0건 규칙을 적용한다. 지수 필수 정보 또는 추가 뉴스 사건이 각각 한 글에 들어가지 않으면 해당 발행을 보류한다. 바뀐 전체 버전은 다시 검증·승인한다.
- 후보 자동 대체는 편성 동결 전까지만 가능하다. PM 동결 후에는 기존 근거에 따른 문안 수정·기사 제외만 새 버전으로 허용한다. 핵심 정정·충돌로 보류된 편성은 문제 기사를 제외해 같은 회차를 우회 재개하지 않는다. 첫 전송 뒤에는 새 버전으로 대체하지 않는다.
- 사실과 출처 해석을 구분하고 선택한 사건의 확인된 변화만 설명한다. 반복되는 AI 총평, 투자 권유·근거 없는 원인·가격 예측을 넣지 않는다.

## R10. 마감·재시도·수동 복구·정정

- 각 글 전송 직전에 발행 가능 창을 확인한다. 아침 09:00부터, 저녁은 18:00 전과 18:10부터 새 요청·자동 재시도를 하지 않는다. 전송한 요청의 결과 조회·기록·한도 정산은 마감 후에도 가능하다.
- 첫 전송 전의 명확한 일시 실패만 기존 최초 외 2회, 1분·5분 간격 재시도를 적용한다. 부분 게시 또는 성공 불명은 자동 재시도하지 않는다. 동일 발행 건의 재실행에도 횟수를 누적한다.
- 수동 복구는 게시물 ID·대상 계정·게시 시각·스레드 연결 관계로 대조한다. 조회 결과에 보이지 않는다는 이유만으로 미게시를 확정하지 않는다. 확실하지 않으면 성공 불명 예약을 유지하고 해당 사건의 새 발행을 막는다.
- 운영자 CLI 복구도 기본적으로 같은 날짜·마감·원승인 버전·한도를 따른다. 일부 게시된 건을 처음부터 다시 게시하지 않는다. 마감 후 단순 잔여 글 이어쓰기는 기본 금지하고 부분 게시 상태를 기록한다.
- 오류 정정은 별도 수동 절차로 둔다. 운영자가 원 게시물 ID·오류·정정 근거·문안을 확인하고 그 정정 건의 실제 게시를 명시적으로 승인할 때 시간·일일 2건 한도 밖에서도 연결 게시할 수 있다. 월 예산·중복·근거 검증은 예외로 하지 않는다. 이는 향후 절차 설계이며 지금 외부 게시를 승인한 것이 아니다.
- 정정 건은 별도 집계하고 일반 뉴스 한도를 환급하지 않는다. 관련 사건의 자동 발행은 정정 완료와 운영자 해제 확인 후 재개한다. 삭제·무기록 덮어쓰기는 하지 않는다.

## R11. 운영자 화면·확인 방식·접근

- 첫 버전은 단일 운영자 계정과 하나의 X 게시 계정을 사용한다. 사이트에서 후보·근거·검증 결과·승인/보류·게시 결과·마지막 정상 실행·수집 공백·비용·중단 사유를 확인한다.
- reviewed의 검토 준비 목표는 아침 07:45·저녁 17:45, 정상 예약 시험의 승인 목표는 07:55·17:55다. 미승인/지연은 마감 내에만 처리한다. 안정화 후 auto는 관리자 접속과 무관하게 검증된 콘텐츠를 정시에 게시한다. Telegram 중요 장애 알림은 R15를 따른다.
- React 화면은 FastAPI의 조회/승인 API만 호출한다. Google 로그인·허용 운영자·만료·CSRF·후보 버전 검사는 서버가 담당한다. Streamlit은 이전 가상 시험용으로 남긴다.
- 인증된 운영자만 근거 조회와 승인 상태 변경을 할 수 있다. 공개 열람·다중 역할·사이트 내 문안 편집·직접 게시·복구 화면은 추가하지 않는다. 세션 만료 시 다시 로그인하고 승인 요청에는 후보 버전을 대조한다.
- 전역 자동 게시 중단·재개는 운영자 CLI로 제공한다. 중단은 수집과 결과 확인을 막지 않으며, 재개해도 만료 승인이나 마감이 자동 해제되지 않는다. 비밀 키는 비밀 저장소/환경 변수로 관리하고 로그·화면·Git에 노출하지 않는다.

## R12. 근거·이력 보존

- 게시문·승인 버전·주장별 근거 위치·원문 URL/ID·시각·검증 결과·발행 ID·비용 기록을 공통 저장소에 둔다. 본문 전문 저장을 필수로 하지 않는다.
- 감사·중복 방지용 최소 메타데이터와 게시 이력은 운영 기간 동안 유지한다. 이용 조건상 허용되는 근거 발췌·요약은 게시 후 30일, 원문과 연결되지 않은 상세 실행 로그는 30일을 초기 보관 목표로 둔다. 실패·정정 조사 중인 자료의 연장은 허용 조건 안에서만 한다.
- 권리자 조건이 더 짧으면 그 조건을 따르고 재현 가능한 근거 보존 방법이 있는지 조사한다. 해시만으로 내용 근거를 재현할 수 있다고 보지 않는다. 핵심 검증 기록을 합법적으로 남길 수 없는 제공처는 보류한다.
- 발행·승인 기록은 재시작 후에도 보존하고 일일 백업·실제 복원 시험을 요구한다. 백업에도 같은 접근·삭제·보존 조건을 적용한다. 클라우드 목표는 PostgreSQL이며 현재 원격 시험은 가상 초안에 한한다. 실제 운영 기록 이전·백업 경로·복원 구현은 후속 검증한다.

## R13. 예산·호출량·한도 소진

- 월 **50,000원**에는 지수·뉴스·AI·X·실행·저장·시험·재시도·결과 조회 비용 및 세금·결제 수수료를 포함한다. 고정 구독료도 사용량과 별도로 선반영한다.
- 월 기준은 KST 달력 월이다. **40,000원 경고**는 새 예산의 80% 운영 추천값이며, 나머지 10,000원은 가격·환율 변동·재시도·복구 여유를 목표로 한다. 환산은 조사일의 확인 가능한 환율과 10% 환율 여유를 적용해 계획하고 청구 시 실제액으로 조정한다. 이는 실제 요금 추정 결과가 아니다.
- 비용 발생 전 확정 지출 + 아직 정산되지 않은 요청 예약액 + 새 작업 최대 비용이 50,000원을 넘는지 확인한다. 40,000원 도달 시 경고하고 50,000원 초과 예상 요청은 실행하지 않는다. 불명 비용은 0원으로 처리하지 않는다.
- 수집은 먼저 ID·시각·지수 관련성·중복으로 걸러 AI 입력을 줄인다. 생성은 후보 버전당 1회, 검증 실패 시 재생성 1회만 허용하며 통신 재시도는 기존 별도 한도를 적용한다. 바뀌지 않은 근거에 반복 AI 호출을 하지 않는다.
- 요청/페이지 상한·작업당 AI 기사 수·입력 길이·출력 토큰 수는 샘플과 실제 단가로 산정할 설정값이다. 산정 전 유료 자동 운영을 시작하지 않는다. 상한에 걸린 검색을 완전 수집으로 처리하거나 본문을 몰래 잘라 검증하지 않는다.
- 예산 부족 시 새 유료 수집·생성·게시를 중단하고 기록 조회·무비용 결과 확인만 유지한다. 선불/후불 과금 지연과 고정료까지 포함해 잔액을 예약한다. 자동 충전·예산 증액·필수 검증 생략은 하지 않는다.
- 40,000원 경고·초과 예상 차단, 공급자 quota/credit 부족은 Telegram으로 통지한다. API 원장은 이 앱의 관측 사용량이며 계정 전체 실제 청구액과 같다고 표시하지 않는다. 앱 요청 차단은 AWS VM 고정 청구를 자동 중단하는 기능이 아니다.

## R14. 완료 판정·시험·조사 인계

- 예약 시험은 대상 미국 거래일 기준 연속 5개 유효 거래일로 진행하며 휴장일은 세지 않는다. 아침과 추가 뉴스의 운영일 차이를 시험한다. 적합한 추가 뉴스가 없을 때 생략한 것은 정상 결과다.
- reviewed에서 정상 조건과 07:55/17:55 승인 완료 시 첫 요청은 아침 08:00~08:05·저녁 18:00~18:05를 목표로 검증한다. auto는 승인을 기다리지 않고 검증 완료와 예약 시각으로 판정한다. 절대 마감 09:00/18:10을 우선하며 정각 실행을 보장한 결과로 취급하지 않는다.
- 5일 동안 모든 발행 문장의 근거·숫자·기간·출처를 운영자가 확인하고, 중복·무승인·마감 후 새 요청·한도 초과·근거 없는 핵심 주장·비밀 노출은 0건이어야 한다. 단순히 게시량을 채우는 것은 합격 조건이 아니다.
- 외부 API 없는 시험으로 정상/0건/부분 수집/지수 누락/시간 미상/기준 후 수정/정정/주말/휴장/서머타임/오래된 기사 재검토/후속 이월/승인 변경/철회/동시 실행/재시작/재시도/부분 게시/성공 불명/예산 소진/복원/길이 초과를 검증한다.
- 장애 시험은 보류·중단·복구가 예상대로 되는지 판정한다. 정상 예약 시험에서 외부 장애로 목표 시각을 검증하지 못하면 해당 실행은 정상 성공으로 계산하지 않고 환경을 복구해 5거래일 시험을 다시 잡는다.
- 사실·승인·중복·한도·상태 복구 결함을 수정하면 관련 회귀 시험과 5거래일 시험을 다시 진행한다. 문구·화면 표시만 수정하면 해당 검증만 반복한다.
- 실제 게시 검증은 시험 실행과 분리한다. 별도 명시적 승인 후 아침 스레드 1호와 추가 뉴스 1건을 게시해 게시물 ID·계정·내용·스레드 연결을 확인한다. 5일 시험 전체를 공개 게시해야 한다는 뜻은 아니다.
- 완료물은 위 시험 근거, 실행 가능한 README, 설정·시작/중단·승인·복구·정정·비용 확인 절차, 미해결 결함 목록이다. 핵심 발행 차단 결함이 남으면 운영 완료로 보지 않는다.
- 5~6주차30시간은 중간 개발 예산이다. 7주차 추가 개발·8주차 초 기능 마무리와 후반 인수는 최신WBS를 따른다. 기존2화면·8API는 현재 구현이며 완료 상한이 아니다. auto의5거래일 시험은 별도다.

## R15. Telegram 중요 알림

- 자동 검증/승인 처리 예외·검증 실패 버전의 발행 시도, 최종 수집 실패/partial, quota/credit/예산 부족, X 부분 성공·성공 불명을 운영자 개인 chat 하나로 통지한다. 일상적 승인 충돌 409·적격 뉴스 0건·개별 기사 제외는 화면 기록으로 남긴다.
- 알림 전에 사건과 중단/보류 상태를 DB에 저장한다. 같은 장애 fingerprint는 열린 동안 중복 억제하고 복구는 1회 통지한다. run/job ID·원인 코드·조치·관리자 링크를 사용하고 비밀·기사 본문·HTTP 오류 원문은 제외한다.
- DB 기록 자체가 불가능하면 X 발행을 차단하고 비밀을 뺀 오류 로그와 Telegram 최선 노력 1회로 남긴다. 이 상태의 알림은 영속 중복 억제가 보장되지 않으며 복구 후 대조한다. 제공처의 429는 단기 rate와 일일 quota/credit 부족을 구분해 알린다.
- 알림 outbox는 최대 3회 전송 시도, Telegram 429 `retry_after` 준수, 실패 상태 보존을 적용한다. 알림 timeout의 중복 수신 가능성을 인정하고 exactly-once를 주장하지 않는다. 알림 실패로 발행 차단을 해제하지 않는다.
- 발신 전용이며 Telegram 승인/게시/예산 변경 명령과 유료 방송은 제외한다. VM/worker 전체 중단을 감지하는 외부 경보는 MVP 후속이다. [계약·실패 시험](../tasks/verification/integration/2주_MVP_구현_계약.md)
