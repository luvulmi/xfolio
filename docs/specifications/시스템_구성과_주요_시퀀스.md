- 기준: 2026-10-31, Asia/Seoul. 목표 설계이며 구성요소별 현행 상태를 함께 표시한다.

## 시스템 구성

실선은 목표 데이터/호출 흐름이며 구현 완료 표시가 아니다. 각 노드의 상태를 따른다. 초기 범위는 Exa/BLS·세 ETF·운영자 검토·AM 모의 전송이다.

```mermaid
flowchart LR
  Y["yfinance 세 ETF: 전환 전"] --> M["Market: 두 지수 일부 구현"]
  Q["Exa: 실측, 제품 미구현"] --> N["뉴스 어댑터: BLS CPI 일부 구현"]
  F["BLS CPI: 제한 파서 구현"] --> N
  O["Fed / BEA / SEC: 후속"] -.-> N
  N --> C["공통 입력 / 근거 검사: 확장 전"]
  C --> L["AI 초안: 생성 함수 일부 구현"]
  M --> D[("PostgreSQL: 8테이블 구현, 새 계약 전")]
  L --> D
  U["React: 검토 목록 / 상세 일부 구현"] --> A["FastAPI: 인증 / 조회 / 승인 8경로 구현"]
  A <--> D
  D <--> W["Python worker: 미구현"]
  W --> X["X adapter: 미구현, 초기 mock"]
  W -.-> T["Telegram 운영 outbox: 후속"]
  X --> D
```

기존 로그인·CPI·승인 시험은 FR-01~08 전체의 인수가 아니다. A01~A07에서 세 ETF·공통 입력·4글·PM 차단·worker를 연결한다. 브라우저는 공급자·DB·봇 비밀에 접근하지 않으며 수집/AI/전송은 HTTP 요청 안에서 실행하지 않는다. 공통 입력 프로필은 [결정 조건](뉴스_입력과_검증_책임.md#미결정-계약과-결정-조건)에 따라 확정한다.

## 목표 배포 구성

B05/B06 후속 목표이며 현재 Caddy/Compose/Lightsail 운영 배포를 확인한 결과가 아니다.

```mermaid
flowchart LR
  B["운영자 브라우저: React"] -->|HTTPS 동일 origin| WEB
  subgraph VM["AWS Lightsail Linux: 목표 VM / Docker Compose"]
    WEB["Caddy / web: 정적 React + TLS"] -->|/api 역방향 프록시| API["FastAPI: 인증 / 조회 / 승인"]
    WORK["별도 Python worker: 단일 프로세스"]
  end
  API <--> DB[("외부 PostgreSQL / Neon")]
  WORK <--> DB
  WORK --> DATA["yfinance / Exa / BLS"]
  WORK --> AI["OpenAI: 초안 생성"]
  WORK --> PUB["X: 초기 mock / 후속 live"]
  WORK -.-> BOT["Telegram: 후속 알림"]
  API --> IDP["Google OIDC"]
```

web/api/worker는 책임 경계다. 단일 VM·worker replica=1과 별개로 DB 점유·사건 claim·정확 버전 재검증이 필요하다. 외부 PostgreSQL에는 API/worker만 연결하고 Windows는 개발용이다. HTTPS callback·재시작·백업/복원은 NFR-02/03/05 인수에 포함한다.

## 1. 수집·검사·초안 저장

FR-01~05,NFR-01/04 · N02/N03/N08/N09/M01/A04/A07. Exa 완료는 설정된 질의·조회창·결과 상한·필수 본문 요청의 완료이며 시장 전체 포괄이나 기관별 페이지/기업 완주가 아니다. running 행 저장은 별도 DB 제약 변경 후의 목표다.

```mermaid
sequenceDiagram
  participant W as Worker
  participant P as ETF / Exa / BLS
  participant D as PostgreSQL
  participant L as AI
  W->>P: 새 완료 미국 거래일 확인
  alt 새 완료 거래일 없음
    W->>D: not_operating 실행 결과, 편성 job 생성 안 함
  else 운영 대상 거래일
    W->>D: 입력별 scope / 조회창 / run 기록
    W->>P: 세 ETF + Exa 설정 요청과 본문 + BLS 지원 입력 확보
    alt 필수 요청 partial/failed 또는 ETF 누락
      W->>D: 실패 범위 기록, 커서 유지, 전체 편성 보류
    else 필수 요청 완료
      W->>D: complete와 확보 시각 / 버전 기록, 완료 커서 진행
      alt 중요 근거 충돌 또는 필수 의미 확인 불가
        W->>D: 편성 보류와 사유, 정상 0건 처리 금지
      else 정상 검토 가능
        alt 적격 뉴스 0건
          W->>D: 정상 선정 0건 기록, ETF 1글 편성 후보
        else 적격 뉴스 1~3건
          W->>L: 검사한 사실 후보와 허용 근거 / claim_id
          L-->>W: 한국어 초안과 주장 연결
        end
        W->>D: 코드 검사 후 근거 참조 / 불변 초안 / AM job 원자 저장
      end
    end
  end
```

07:30까지 실제 확보한 버전만 사용한다. 개별 후보의 권리/본문 부족은 제외·보류로 기록하고 필수 요청 실패와 구분한다. 기계 검사 통과는 사람의 의미 검토나 공개 이용 허가가 아니다.

## 2. 전체 승인·버전 충돌·예약

FR-05~07,NFR-02/03 · A01/A02/A04/A05/A07. 현행 승인 기반 위에 새 프로필·review_checks·4글 검사가 추가될 목표다. DB 트랜잭션 안에서 외부 X를 호출하지 않는다.

```mermaid
sequenceDiagram
  participant U as 운영자 / React
  participant A as FastAPI
  participant D as PostgreSQL
  U->>A: 상세 조회, 근거와 현재 버전 대조
  A-->>U: version / revision / 검사 / 허용 동작
  U->>A: approve + expected version/revision + 확인 3개 + 멱등 키
  A->>A: 세션 / 운영자 / Origin / CSRF 확인
  A->>D: 한도 잠금 / job 잠금 / 멱등 요청 조회
  alt 같은 키와 같은 본문 재시도
    D-->>A: 최초 결과와 현재 상태, 새 예약 없음
    A-->>U: replayed와 현재 상태
  else 같은 키와 다른 본문 또는 버전/revision 충돌
    A-->>U: 409, 최신 상세 재검토 필요
  else 새 결정
    A->>D: AM / 버전 / 프로필 / 근거 / 기한 / 전체량·비용 검사
    alt 검증 또는 한도 실패
      A-->>U: 승인 거절과 안전한 사유
    else 모든 조건 충족
      A->>D: posts·사건 claim·비용 예약 + 감사 + scheduled 커밋
      A-->>U: 예약됨, 상세·목록·summary 재조회
    end
  end
  opt 이후 운영자가 보류 요청
    U->>A: hold + 현재 version/revision + 사유 + 새 멱등 키
    A->>D: worker와 같은 job 잠금으로 경쟁, 현재 상태 재검사
    alt 첫 전송 전
      A->>D: 확실한 미전송 예약/claim 해제, held와 감사
    else 첫 전송 시작 후
      A->>D: stop_requested와 감사, 잔여 중단·기존 결과/불명 예약 보존
    end
    A-->>U: 현재 상태, 이미 송신한 요청 취소를 보장하지 않음
  end
```

POST timeout은 성공으로 추정하지 않고 상세부터 재조회한다. 보류에는 확인 3개를 요구하지 않는다. 상세 허용 동작과 오류 형식은 API를 따른다.

## 3. worker 점유·글별 전송·결과 저장

FR-08,NFR-03/04 · A03/A05/A06/A07. 초기 인수는 mock이며 후속 live는 명시 요청 범위에서 검증한다. 아래 loop는 글마다 계속 조건을 만족할 때만 다음 글로 진행한다.

```mermaid
sequenceDiagram
  participant W as Worker
  participant D as PostgreSQL
  participant P as 동결 근거 출처
  participant X as X adapter
  W->>D: due job 잠금·점유, 승인 버전 / 기한 / 예산 확인
  D-->>W: 유효 lease와 동결 버전 또는 처리 불가
  loop 점유·기한·중단 조건을 통과한 각 글
    W->>P: 승인된 동일 근거 버전의 유효성 재확인
    alt 정정 / 확인 실패 / 중단 요청 / 마감 / 점유 무효
      W->>D: 신규 송신 차단, 미전송·기존 결과 보존
      Note over W,D: 첫 시도 전 보류/만료, 이후 결과 기준 집계와 잔여 중단
    else 계속 가능
      W->>D: 잠금 아래 재검사, sending / first_attempt / attempt_started 커밋
      W->>X: 승인된 정확 문안, mock 또는 허용된 live
      alt 성공 확인
        X-->>W: mock 결과 또는 확인된 live post_id
        W->>D: 동일 attempt 결과 / 글 상태 / 비용 원자 저장
      else 확실한 실패
        X-->>W: 안전한 실패 코드
        W->>D: 실패·비용·잔여 중단 기록
      else timeout 또는 결과 저장 불확실
        W->>D: 가능한 경우 unknown 기록, 예약 보존·자동 재송신 금지
        Note over W,D: 시작 기록만 남은 시도도 재시작 시 결과 대조 대상
      end
    end
  end
  W->>D: 전체 published / 일부 성공 partial / 불명 우선 unknown / 성공 없는 실패 집계
```

unknown이 하나라도 있으면 편성 집계도 unknown을 우선한다. 일부 성공과 확실한 미전송/실패는 partial, 전체 확인 성공만 published다. 첫 전송 후에는 버전 교체·재승인으로 우회하지 않는다. 모의 결과에는 실제 X ID/링크를 만들지 않는다. 정정·복구 절차는 운영 정책과 B04를 따른다.
